# UI 文案守卫（ui-copy-check）

一句话信念：**用户是"完全与开发隔离"的体验者，他在界面上的全部知识来自界面本身。** 凡是要写进用户可见界面的文案，都不能要求用户知道界面以外的东西——系统内部结构、技术机制、实现原理、项目代号、迭代状态。

「界面本身」不只是这一条文案，而是整页环境：所在面板、区块标题、同行状态标签、字段占位符都在向用户供信息。写一条文案前先盘点环境已经说清了什么，文案只补环境没说清的差额——把环境已指认的对象再写进标签，不是更清楚，是更啰嗦。

本 skill 在两种时刻介入：
1. **检查模式**：用户要求检查已有 UI 文案时，逐条审计、分类、给改写。
2. **生成守门模式**：正在为用户界面写面向用户的文案时，把用户视角戴在生成阶段，写完顺手过一遍分类。

## 它在堵的失败模式

这几类多数来自同一条根因——agent 的注意力还停在自己（开发者/项目参与者）的语境里，没切换成"使用者"的眼睛。认清根因，改正时就不只是一个词一个词地换，而是整体切换叙事视角。最后一类（层级错配）的根因不同：信息本身不难懂，但挂错了层级。

1. **系统解释当 UI**：针对系统内部、开发者/项目参与者的解释性、描述性文案，被误当成"页面里该显示的文字"搬进界面。
2. **技术性措辞**：面向用户的文本用了行话、缩写、模块/接口/字段名、技术概念，用户没有这份词汇表。
3. **参与者上下文**：文案依赖只有项目参与者才知道的信息（内部代号、迭代/迁移状态、流程内部步骤、内部系统名）。
4. **视角倒置**：主语是系统/开发者而不是用户，讲"系统做了什么"，而非"你能得到什么、能做什么"。
5. **冗余复读**：把页面环境已经指认的信息（在哪、谁的、对谁）再写进标签。与前四类同一根因的镜像面：前四类是没切换成用户的眼睛，这一类是没看见页面已经替用户把话说了一半——每条文案都被当成孤立的字符串，兜底全套上下文。
6. **层级错配**：把作用于整体的信息挂到单个对象的标签位上，每个词都通俗、整体仍误导。典型如任务状态后面跟一个全局并发计数——用户会以为那是这个任务的属性。

## 判定工具（四把尺）

四把尺用于逐条判断是否错位；下面的七个标签 = 6 类错位 + 1 类通过。

逐条文案拿不准时，用这四把尺子，任一命中即错位：

1. **"放进内部文档违和吗"**：这段文案放进一份"给项目参与者的内部技术说明"里毫无违和？→ 它不是面向用户的 UI 文案。UI 文案应该反过来：放进用户界面才通顺，塞进内部文档反而突兀。
2. **"界面外知识"尺**：用户要理解这句话，是否必须知道界面之外的事（实现方式、内部命名、代号、流程内部）？是 → 错位。
3. **"主语"尺**：把主语改成"你 / 你能 / 你已经"，句子是否立刻更清楚？是 → 原句站在系统视角。
4. **"环境已说过吗"尺**：把文案里的限定词逐个删到最短，读者在它所在的位置（面板、区块、行、邻近状态标签）能否仍无歧义地指认它说的是什么？能 → 删。只有同屏存在真正会混淆的竞争概念时才加限定词。这把尺不对 `aria-label` 使用——无障碍树是扁平列表，没有视觉邻近环境，对象名必须写进 aria-label 自身。

## 逐条分类（检查时先给每条文案打一个标签，再下判定）

1. **可接收（通过）**：用户不借助任何界面外的知识就能理解，直达他的行为/处境。　例：「保存吗？保存后，大家立即看到你的最新版本。」
2. **系统解释性（硬伤）**：在向用户解释系统内部结构、机制、实现原理、数据流。典型信号：出现"模块 / 接口 / 服务 / 同步 / 异步 / 入库 / 链路 / 后端 / 队列 / 缓存 / 实时推送 / 自动重试"等技术名词，或整句在解释"系统是怎么工作的"。
3. **技术性措辞（硬伤）**：用户词汇表外的行话 / 缩写 / 专有名词（WebSocket、CRUD、token、幂等、DTO、schema、灰度、SLA…）。判定：这段换成大白话（"这个功能 / 这里 / 下一步"）后是否明显更通顺？是 → 原词是用户不掌握的行话。
4. **参与者上下文（硬伤）**：依赖只有内部人知道的信息（内部代号、票号、迭代/迁移状态、内部系统/部门名）。用户看到只会困惑，有时还暴露了不该暴露的内部结构。
5. **视角倒置（改进点，常伴随以上出现）**：以系统/开发者为叙事主体。例："系统将实时同步"——用户关心的只是"我什么时候能看到最新结果"。
6. **冗余复读（改进点）**：文案重复了页面环境（所在面板、区块标题、同行状态标签）已指认的信息。证据句式：删掉这个限定词，读者在原位置仍能唯一指认。不是硬伤，但有真实的扫读成本，且会传染——一处加了限定，复审容易要求别处对齐，越改越长。
7. **层级错配（改进点）**：把全局信息塞进单个对象的标签位。典型信号：一行文案的主语是"这个对象的状态"，后面却跟一个作用于整个集合的计数，例如「待生成 · 图生图（在飞 2/5）」里的 `2/5` 是全局并发数。判定：括号里 / 后缀里的数字，主语是这个对象还是整体？是整体 → 挪到集合层级的标题或汇总位，不要挂在单项后面。这类问题逐词替换解决不了，要调布局。

**术语的红线**：品牌/行业术语（"订单 / 发票 / 退款 / 订阅 / 导出 / 打印"）用户本来就会用，**不是问题**。判据永远是"这个词在不在这位用户的词汇表里"，而不是"它是不是专业术语"。反过来，一个看起来无害的词如果只有内部人才懂（"工单 / 排期 / 灰度"取决于目标用户群），一样要改。

## 改写原则

- **结果优先于机制**：写用户"得到了什么 / 接下来会怎样 / 可以做什么"，不写系统"怎么做到的"。
- **行为导向**：回应"用户此刻在想什么、在做什么"。"已保存"优于"数据已入库"；"正在处理，稍后回来查看结果"优于"任务异步执行中"。
- **删除优先于改写**：某行文案只服务于项目参与者对齐、删掉用户毫无所感 → 它不属于界面，直接删或下沉到内部文档。
- **状态与空态是重灾区**：agent 写"成功 / 失败 / 空态 / 加载中"时最容易退回开发者视角。空态优先写"还没有 X，去创建第一个吧"（示例，按语境调整；判据是用户能知道下一步）；错误提示要落到"现在发生了什么 + 用户能做什么"。
- **含糊 ≠ 简洁**：反例「请求失败，请稍后重试」的问题是**没说什么失败了、也没说能做什么**，不是因为它短。反过来说，短句完全可以合格——「生成超时，请重试。」现象具体、下一步明确。不要为了避开"系统话术"就加"这次…了""可以…"之类的缓冲语，那只是把含糊换成了啰嗦。判据始终是"信息是否齐备"，不是句子长短或语气冷暖。
- **需要的后果用用户能测的表述**："保存后，别人立即看到你的更改"，而不是"更改将通过实时通道推送"。
- **先给最短版，再按冲突加词**：改文从最短能指认的版本写起；要加限定词，必须指名它防的是哪个同屏冲突，说不出冲突就不加。可见文案靠页面环境省词；`aria-label` 是例外，自带对象名。

## 工作流程

0. **确定扫描面与排查方向**（检查模式必做，漏检主要发生在这里）：
   - **用户可见字符串不止在渲染层**。除了 JSX 文本，还包括：后台 / service worker 直接下发给界面的提示（如 `message:` 字段）、被 `catch` 后拼进提示的内部错误（`复制失败：${error.message}` 会把内部异常原样外露）、`throw new Error()` 里的文案。只扫 `*.tsx` 会系统性漏检这类。
   - **内外分界**：`//` 与 `/** */` 注释里的工程术语是工程师内部语言，不算文案问题；同等用词出现在 JSX 文本、`message:`、`throw new Error()` 里才需要整改。判断一个字符串会不会被用户看到，看它有没有渲染出口，而不是看它读起来像不像人话。
   - **两种排查方向都要走**：正推 = 拿一份内部术语表（在飞、入库、链路、载荷、配额…）去代码里搜，快且能兜住不显眼的词；倒推 = 从每个用户可见字符串出发，逐个问"用户读到这句需要界面外的知识吗"，能发现术语表没收录的新黑话。只做正推会漏掉未预设的词，只做倒推容易机械逐词替换而不看整句语义。
   - **改文案前先搜测试断言**：文案常被测试用 `toContain('…')` 固定，改文案必须同步更新断言，否则用例变红。
1. **定对象**：待检查的界面 / 文案集合；若是生成守门模式，则边写边按本 skill 过。
2. **逐文案**：每条打标签（七个之一）+ 给证据（至少一句，能引用原词，说明为什么错位）。
3. **用户视角还原**：先写"用户此刻在界面上的真实处境"——他看到了什么、想干什么、**页面环境已经明示了什么**（所在面板/区块/行、可见状态标签、占位符），再给改文——改文只补环境没说清的差额，对着处境写，而不是对着原句逐词替换。
4. **产出**：按自适应输出格式。

## 自适应输出

**轻度（默认，单屏 / 少量文案）**——逐条：
- 所在区域 + 原文 → 标签 → 证据 → 可整行替换的改文。

**重度（系统性信号）**——以下任一信号升级为整体诊断，不得仍给零散逐条：
- 整页 / 整流程的文案多处错位，或同一用户动作的反馈链（触发 → 加载 → 成功/失败/空态）全部站在技术视角
- 页面大量出现模块/实现类名词，系统性把用户界面当内部说明写
- 引导语、空态、错误提示整块是"写给开发看"的占位式文字

重度输出包含三段：
1. **整体诊断**：这页 / 这条流程的文案整体站在谁的视角，根因是一处还是多处。
2. **分类清单**：逐条 原文 → 标签 → 严重度。
3. **分级改造**：分"必须改（硬伤）"与"建议改（视角倒置 / 冗余复读 / 层级错配）"两级，每处给整行可替换的改文。

## 边界（Do NOT）

- 不评价视觉 / 交互 / 可达性——只盯文案的用户可懂性。唯一越界到结构的情形是「层级错配」：当某项信息挂在错误的层级上时，指出它该归属哪一层（单项还是集合）是文案可懂性问题，但具体怎么排版、放哪个像素位不归本 skill 管。
- 不评价产品需求与价值。
- 不把技术性措辞当"高级 / 严谨"豁免——技术正确不豁免用户可懂性。
- 不擅自改写用户明确保留的品牌 / 行业术语，也不把"用户本来就会用的词"误判成行话。
- 不替用户拍板"全量重写"的投入——交出改造清单与轻重，投入多少由用户定。
- 不因为"用户以后会习惯""有客服兜底"就放过必改项。

## 沟通风格

- 中文。结论先行，证据跟上。
- 改文必须是可整行替换的具体文本，不给"让它更友好一点"式形容词。
- 每给一处问题，至少给一条等价改文；一处都改不出来时，判断它是否根本不属于界面。
