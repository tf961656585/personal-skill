# 主从模式（master-subagent）

## 为什么：注意力预算是根本约束

每个窗口的注意力是有限资源：上下文越长，模型准确召回和长程推理能力越退化（context rot）；多职责共享同一窗口时，各职责的关键信息会互相挤进注意力的中段盲区（Lost in the Middle 的 U 形曲线）。主从模式把执行细节隔离在子代理窗口，主窗口只保留高信号内容：任务目标、委派契约、蒸馏结论、用户沟通。

量级参考（Anthropic 官方实践）：子代理可以消耗数万 token 做探索，回传主 agent 的只有 1,000–2,000 token 的浓缩摘要。这个比例就是主从模式的价值所在。

## 角色分工

**主 agent（唯一面向用户）**：理解意图、拆解任务、写委派契约、验收结果、汇总决策、与用户沟通。不做深度探索，不读大量原始材料——那是子代理的事。

**子 agent（面向主 agent）**：在独立上下文完成边界明确的子任务，返回蒸馏结论。它的"用户"是主 agent，返回内容要为主 agent 的验收服务。

默认单层：子代理不再派孙子代理，除非主 agent 显式授权。层级一深，主 agent 就失去全局视野，注意力隔离也逐层失效。

## 红线：禁止代劳

子代理失败或结果不合格时，主 agent 的合法动作集只有三个：

1. **修正契约后重新委派**：分析失败报告，修正任务描述（换实例、加约束、补充上下文），派新子代理。
2. **resume 原实例**：保留子代理已积累的上下文，附失败信息让它从断点自适应续跑（适合瞬时错误、工具报错类失败）。
3. **上报用户**：达到重试上限（默认 3 次）仍失败，停手，把失败事实、已尝试路径、建议选项交给用户拍板。

任何情况下，不得把子任务的执行工作并入主 agent 自己的行动轨迹。

代劳的真实代价不是"多做了一点事"，而是：失败任务的报错、重试痕迹、中间产物全部灌进主窗口，注意力预算被挤占，主 agent 失去路由、验收、用户沟通所需的上下文余量——这正是主从模式要防止的事，代劳等于拆了这个模式本身。

最常见的破例借口是"这个任务很小，自己做更快"。判断标准不变：问题不是它小不小，而是它属不属于已委派的子任务。已委派出去的，回到合法动作集三选一。

## 委派契约（主 → 子）

子代理白板启动，看不到主对话历史，所以每条委派必须自包含。四要素缺一不可：

1. **目标**：要什么结果，验收标准是什么。
2. **输出格式**：返回什么结构（建议：结论 → 证据位置 → 未决问题），量级上限。
3. **工具与信源指引**：已知的文件路径、命令、该用的信源——主 agent 已知的具体事实直接写进去，别让子代理重新搜。
4. **任务边界**：不做什么；多个子代理并行时，各自的切分线在哪，保证互不重叠、不留缺口。

给边界和已知，不给预设步骤：固定步骤在前提错误时是死重，还会废掉子代理的现场判断。调查类任务给问题不给步骤；查找类任务直接给路径和命令。

**写进契约的「已知事实」要标注请核实——含语义性断言**：路径、行号、文件名之外，凡契约里的语义性断言（文案的语义与后果、数据去向、行为边界）若未经主代理亲自核验，同样要标注「请核实」或先核实再写。转述漂移与语义失实会顺着契约传播给下游并被忠实执行；曾有主代理把文案的语义与后果写错，子代理照写进确认框，验收时才靠后端核实纠正。

**验收标准对齐交付门禁**：实现类委派的验收标准必须覆盖 delivery-check 的全部适用项。子代理不会自己想起这些项——契约不点名就只能靠主 agent 收尾补做，甚至整项漏掉。

## 设计评审类子代理的协调协议

"设计专家评审 + 实现子代理修复"的多轮验收场景，加载 `references/design-review-protocol.md`：评审简报预装、逐 ID 对账、图证规则、修复与验证拆分。其他委派场景不加载。

## 返回契约（子 → 主）

- 返回蒸馏结论，不返回原始材料（dump、日志、文件全文）。大产物落盘，回传引用路径。
- 结构：结论 → 证据位置 → 未决问题/风险。
- 失败必须返回结构化失败报告：失败类型（瞬时错误 / 前提错误 / 能力不足 / 被外部条件阻断）、已尝试路径、建议修正方向。这份报告是主 agent 决定 resume 还是改契约重派的唯一依据。

## 验收

- **判结果不判路径**：子代理可以走不同的合法路径到达同一目标。
- **要证据不要断言**：测试输出、命令结果、diff，而不是"已完成"。
- **「已删除/已清理」类断言按符号级核验定性**：报告里的「删除 X」没区分「删除符号」和「保留符号名、重写内部实现」——后者是合理工程决策（复用函数名降低调用方改动面），但按字面信任会漏掉真残留，按字面判死会误伤重写。主 agent 收到这类报告后先 grep 旧符号清单，命中就读命中点做三分定性：仍被活跃消费 = 未删；只是注释里的历史说明 = 可接受；函数被整体重写 = 换表述理解（删的是旧实现不是符号）。用门禁结果加命中点语义综合判定，不凭报告措辞下结论。相应地，重构类委派契约可预先要求子代理回传「符号级改动清单（删除/新增/重写分列）」，从源头消歧。
- **不重跑复核**：不重新执行子代理的搜索和阅读来"再确认一遍"——那等于把隔离出去的上下文再吞回来。验收靠契约里的验收标准加子代理回传的证据。

## 共享层先行（跨执行单元并行）

当任务拆成多个执行单元并行推进，且这些单元共同依赖同一套基础层（公共契约、共享组件、外壳/导航、配置、数据模型、状态原语、构建或测试脚手架等）时：

- **先定共享层，再 fan-out**：由主 agent 或单一子 agent 先定义并落地共享层（契约 + 唯一实现 + 一个参考用例）。共享层未落地前，不派发依赖它的执行组；否则各组只能基于各自的假设补一套，合并时形成并行体系。
- **执行组的验收包含跨组一致性**：共享契约的消费方式、命名、状态处理、错误与边界行为必须一致；本组构建通过、局部行为正确只是必要条件，不是充分条件。
- **共享层的变更权归单一 owner**：执行组发现共享层缺口时回报，不自行修改或另起一套实现；确需变更由 owner 统一落盘后再通知各组。
- **主 agent 收尾做跨组对照**：抽检或量化核验各组对共享层的实际使用，而不是只汇总各组自检报告。
- **划分线要按“谁拥有共享层”校准**：如果多个组的任务无法在不改共享层的前提下独立完成，说明切分线错了，先重划再派发。

共享层不限于代码：也可以是统一文案口径、统一数据格式、统一验收脚本。判断标准是“多个执行单元是否必须对同一件事保持一致”。

反例：各执行单元各自发明一套基础实现，单元内都通过，合起来形成多套并行体系。

## 并行与伸缩

- 相互独立的子任务并行委派，一批 3–5 个；有依赖关系的串行。
- 按复杂度伸缩投入：简单查找 1 个代理；直接对比 2–4 个；复杂探索 5 个以上且职责明确划分。简单任务不要派一堆代理，委派的上下文传递本身有成本。

## 派发后的等待协议

子代理派发出去后，主 agent 先回答两个问题再决定下一步：

1. 下一步是否依赖子代理结果？
2. 有没有不依赖任何未归结果的独立工作可做？

- **下一步依赖结果**：停手，等结果返回再继续。这里的等待是停着等，不是空转——禁止反复查询子代理状态、循环刷新列表，或启动与任务无关的动作来"填时间"。
- **有独立工作可做**：可以继续，但开始前确认它不消费未归结果；依赖链上的动作一律等对应结果到齐。
- **共享工作区副作用**：子代理在跑期间，主 agent 只做只读或不落地的独立工作。**放行类门禁（项目的构建 / 类型 / 边界检查 / lint / 全量测试）必须等所有子代理落定后再跑**——子代理编辑中的半成品（未使用变量、未接线的中间态）与临时取证文件都会让门禁报红，白等一轮构建，且容易把假红误判成本轮真红去改代码。命中报错文件属于某子代理正在改的产物时，先判"它是否还在编辑"，不要直接改代码。（注意门禁的扫描范围可能覆盖子代理的作业面——如 lint 覆盖原型目录，别假设只有 `apps/` 类改动才会互相干扰。）
- **选对等待方式**：单个子代理、结果回来前没有独立工作可做、且不需要续跑时，用同步等返回的派发方式；需要多轮续跑或批量并行时，用后台可续的派发方式，统一派发后等完成通知。
- **验收与汇报门槛**：已到的独立结果可以逐个收纳，但验收、汇总、向用户汇报必须等所有依赖结果到齐；缺项不下结论。

## 身份与可见性

- 子代理查询能力通常只返回主 agent 派生的后代，不返回自身、父级或兄弟节点；不要试图用查询能力定位"自己是谁"。
- 后续续跑、中断子代理所需的句柄，以委派时的返回值为准，派发后立即记录；查询列表只是找回入口的辅助，不是句柄的来源。
- 当环境的续跑/中断能力只覆盖直接子级时，深层后代只能中断；需要给深层后代传话时，通过其直接父级转达。

## 适用边界（何时不拆）

- 一两步即可完成的小任务：直接做。委派的契约编写和上下文传递成本高于收益。
- 需要主 agent 亲自理解的判断：设计取舍、拍板、验收标准的制定。外包后主 agent 失去拍板所需的上下文。
- 子任务间强依赖、必须共享同一份上下文的工作：不适合拆分，单线程做。拆开后各子代理基于相互冲突的隐含假设行动，产出无法合并。
- 低价值任务：多代理的 token 消耗是单代理的数倍，任务价值要撑得起这个成本。

## 失败恢复协议

按失败类型选路径，不是机械重试。

**续跑（resume）的前提**：只有采用可续派发方式创建、且仍处存续期的子代理才能续跑；同步一次性派发创建的子代理在返回后即终止，失败只能走重派或上报。派发前先判断任务有没有续跑需要：可能需要多轮修正 → 用可续派发；一次定论即可 → 用一次性派发。

- **瞬时错误**（限流、超时、工具报错）→ resume，附失败信息让子代理自适应。
- **前提错误**（任务描述不清、边界划错、上下文缺失）→ 修正契约后换实例重派。不要 resume——旧上下文已被错误前提污染。
- **同类失败重复出现** → 熔断：换方案、换信源、换切分方式重派，不在同一路径上叠加重试。
- **自助恢复穷尽**（默认 3 次）→ halt，结构化上报用户：失败事实、已尝试路径、建议选项。从用户拍板处继续，不从零重来。

## 环境能力适配（跨 harness）

本技能只约束行为，不绑定任何具体工具注册名。执行前先把抽象能力映射到当前环境，映射结果写进当次委派契约：

| 能力 | 语义 | 缺失时的降级路径 |
|---|---|---|
| 可续委派 | 创建子代理并拿到句柄，完成后仍可续跑、可中断 | 降级为一次性委派；失败只能重派或上报 |
| 一次性委派 | 同步等待结果，返回即结束 | —— |
| 续跑 | 向既有子代理追加消息，沿用其上下文 | 改契约重派新实例，或上报 |
| 中断 | 取消子代理当前工作 | 等其自然结束；期间不得推进依赖链 |
| 后代查询 | 查看直属后代/子树的存在与状态 | 不查询，只信完成通知或返回结果 |
| 完成通知 | 子代理结束时环境主动告知主 agent | 用一次性委派同步等待；禁止轮询模拟等待 |

环境的实际边界可能更严（例如续跑只覆盖直接子级、查询不返回自身）。映射结果与上述语义不符时，以三条底线为准：不代劳、不空转、依赖未归不动依赖链；并在当次委派契约中写明实际调用方式。

需要具体环境的注册名时，读 `references/environment-mappings.md`；新增环境时只追加该文件，不改本正文。

## 边界（Do NOT）

- 不把本规范当模板机械套用；先过「适用边界」判断该不该拆。
- 不在主窗口执行任何已委派出去的子任务，无论它看起来多小、多快。
- 不让子代理的原始探索材料进入主窗口；发现委派契约漏了输出格式约束时，补契约而不是将就收下大段 dump。
- 不替用户拍板失败后的走向；重试上限到了就上报。
- 不把等待做成轮询循环；当前环境没有完成通知时，改用一次性同步派发等待结果，而不是反复查询。
