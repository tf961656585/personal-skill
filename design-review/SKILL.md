# 设计层审查（design-review）

审查对象是**多份设计层产物之间**的关系：spec、设计文档、已验收原型。代码不是审查对象。这个边界是本 skill 存在的理由——agent 的默认姿态是下沉到实现，设计审查一旦滑进代码，产出就从"设计缺陷清单"变成"对齐偏差清单"，两者回答的是完全不同的问题。

单份产物内部的写作质量与内部一致性归 spec-guide 场景 B；本 skill 只在至少两份产物之间做对照。

## 开工前：锁定范围

- 从用户派发中提取审查对象清单；派发没给清单时，先自查仓库的设计层产物布局（spec 目录、设计文档、原型入口），列出清单并说明，再开始。
- STRICTLY READ-ONLY：本任务不修改任何文件。审查的产出是报告，修复是另一个任务。
- 如果派发措辞同时要求"检查设计"和"检查实现对齐"，向用户确认拆成两个任务，或按设计层审查优先、对齐检查另计。
- 如果派发实际只要**一份 spec 的写作质量**（完整性 / 可验证性 / 时态纯净度），那是 spec-guide 场景 B 的域——一句话指出并建议改走场景 B，不在本 skill 内展开。

## 证据来源

- 只允许设计层产物相互对照：spec ↔ spec、spec ↔ 设计文档、spec/设计文档 ↔ 已验收原型。
- 代码、测试、构建产物不是证据来源。唯一例外：用户明确允许用代码佐证某个设计疑点时，可作附注证据，但报告主语仍是设计层条目。

## 检查维度

1. **断链**：引用的概念/条目/文档不存在；术语被使用但无定义；流程描述中断（入口到结果走不通）；状态有写入方无读取方或反之。
2. **契约矛盾**：两处对同一概念的口径冲突（语义、边界、所有权、约束）。
3. **职责重叠 / 空白**：同一职责被两个模块/文档同时认领；或关键职责无人认领。
4. **术语漂移**：同一概念多个名字，或同一名字指多个概念。
5. **状态所有权不清**：状态的所有者、读写路径、生命周期没有唯一口径。

断链维度（第 1 条）分两层执行：文件引用层（frontmatter 路径字段、Markdown 相对链接指向不存在的文件）先跑 `python3 "$HOME/.agents/skills/spec-guide/scripts/design_lint.py"` 机械裁决，其结果直接并入报告；agent 聚焦脚本覆盖不到的语义层断链——术语被使用但无定义、流程描述中断、状态有写入方无读取方。

## 输出契约

报告按维度分组，每条 finding 包含：

- 维度分类与严重度（阻断级 = 契约矛盾/断链导致主链不闭环；次要 = 漂移/重叠/空白）；
- 位置引用：`文件:行` 或章节锚点，主语必须是设计层条目；
- 冲突双锚点：矛盾类 finding 必须同时引用两处来源（review X against Y），不接受只引一处的"我觉得不对"。

**Do NOT flag**——以下不属于本任务输出，写进报告即视为跑题：

- 实现与设计的对齐偏差（"代码没按 spec 做"）；
- 代码质量、风格、测试覆盖问题；
- 实现层的重构建议。

## 与相关 skill 的边界

- **spec-guide 场景 B**：单份 spec 的内部质量（完整性、可验证性、时态纯净度、内部一致性）归它；本 skill 只做多份产物之间的对照，不接管单份 spec 的内部审查。

## 修复出口

- 每条 finding 给出设计层修复路径：收口为单一口径（指出建议保留哪一处）、修订哪份文档的哪一节、或标注"需用户裁决的取舍"并上浮。
- 不产出代码改动建议；发现实现偏离设计时，记录为"另起实现对齐检查任务"的线索，一句话带过。
- 修复动作不自动执行：报告交付后由用户裁决，修订设计文档走 spec-guide 场景 C。
