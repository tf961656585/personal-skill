# 产品化表述：让非技术读者看懂软件上下文

## 为什么需要这个 Schema

Agent 经常刚看完代码、翻完 spec、理清调用链，然后直接把这些压缩过的内部结论抛给用户。非技术读者没有经历这个过程，看到一串类名、服务名、调用链时，不是他们水平不够，是信息不对称没有被抹平。

本 skill 的目标：让软件设计者、决策者、产品经理在不接触代码的情况下，也能看懂“这是什么、现在怎样、为什么重要、需要我做什么”。

核心手段有两个：
1. **业务语言优先**——把内部实现翻译成用户可感知的行为和结果；
2. **固定 Schema**——每次输出结构一致、自包含，读者拿到任何一段都能独立理解。

## 触发判定

默认适用：只要回复面向用户，就按本 skill 的口径组织——默认读者是产品经理，判断标准见 AGENTS.md「沟通对象」（不看代码、不查文件，能否据此知道发生了什么、有什么影响、要做什么）。

以下情况是明确信号，命中时不得省略本 skill：

- 用户明确要求“用产品/业务语言解释”“说人话”“给 PM/老板/非技术同事看”“不要讲实现细节”；
- 回复中即将出现类名、函数名、文件名、模块名、服务名、API 路径、表名、依赖名、配置项、分支名、commit 等内部标识符；
- 需要把代码现状、设计草案、问题排查、重构方案、技术债等翻译成业务影响和决策上下文。

技术模式收窄：用户明确要实现细节、自己给出代码线索 / 路径，或已进入纯实现层语境时，可以展开技术语言；但仍以一句业务结论开头，内部标识符放在「技术备注」或用户要求的细节段。

轻量输出：短问答、执行确认、进度回复不套完整模板——先给一句业务结论和必要影响，技术细节按需；完整模板用于状态汇报、方案说明、问题排查、设计讨论等读者要据此行动的输出。

如果输出里包含“需要你拍板/确认/选一个”，还必须叠加 `decision-question` skill 的六段决策简报（见下文「与 decision-question 的关系」）。

## 固定输出模板

除非用户明确要求别的格式，否则按以下模板输出。短回复可只保留「一句话结论」和当前需要的字段，不为了凑结构填充空段。字段顺序即阅读顺序。

```markdown
# {业务标题}

## 一句话结论
{用业务语言一句话说清：这是什么 / 要干什么 / 需要什么}

## 这是什么
{这个功能/问题/改动在用户或业务流程中是什么；
 内部概念首次出现必须配业务解释：业务含义（内部名）}

## 现状与证据
{当前状态 + 证据来源标签：[已实现] / [设计中] / [已验收原型] / [未核实]；
 有数据就写具体数字和影响范围}

## 为什么重要
{对用户/业务的价值、风险、成本；做与不做的后果}

## 需要你做什么
{明确动作：仅同步 / 确认 / 拍板 / 提供信息；
 如果是拍板，必须附选项、代价、我的倾向}

## 技术备注（选填，研发核对用）
{内部标识符、实现细节、文件/模块/服务名；
 非技术读者可完全跳过}
```

### 字段规则

| 字段 | 必填 | 规则 | 正例 | 反例 |
|---|---|---|---|---|
| 标题 | 必填 | 业务语言命名，不含内部标识符 | 「支付成功但页面显示失败的处理方案」 | 「OrderService checkout 409 修复」 |
| 一句话结论 | 必填 | 非技术读者 10 秒内看懂重点 | 「少量用户会遇到已扣款但页面仍显示失败，需要定一个处理策略。」 | 「`RetryTemplate` 配置需要调整。」 |
| 这是什么 | 必填 | 用用户/业务视角解释；内部概念首次出现即翻译 | 「用户在购物 App 提交订单并完成支付后，系统应该显示支付成功。」 | 「`OrderService` 负责订单闭环。」 |
| 现状与证据 | 必填 | 事实 + 证据来源；不把 spec 当已实现 | 「已核实：线上存在重复支付通知，当前代码没有正确识别同一笔订单。」 | 「代码里 `idempotency_key` 冲突。」 |
| 为什么重要 | 必填 | 说清用户影响、业务风险、成本 | 「会让用户以为支付失败并重复支付或找客服，影响信任和客服成本。」 | 「这是稳定性问题，建议尽快修。」 |
| 需要你做什么 | 必填 | 明确动作；拍板时给选项+代价+倾向 | 「请拍板：重复通知是直接忽略，还是向支付渠道再确认一次？」 | 「需要你确认一下方案。」 |
| 技术备注 | 选填 | 隔离区，仅供研发核对 | 「`OrderService.checkout` → `PaymentGateway`；`idempotency_key` 冲突返回 409。」 | （放在正文当主体） |

## 翻译规则

### 1. 行为化

把“系统内部动作”翻译成“用户可感知的行为 / 结果”。

- ❌ `UserService 调用 CouponValidator 校验优惠券`
- ✅ `用户下单时，系统会检查这张优惠券是否还能用`

### 2. 首次出现即翻译

内部名词第一次出现时写成：`业务含义（内部名）`。

- 例：`负责订单超时关闭的定时器（OrderCloser）`

解释里如果又引入新术语，继续展开，直到落到读者已知概念。

### 3. 证据来源标签

- 代码里已实现 → `[已实现]`
- spec 里设计但未核实 → `[设计中，实现状态未核实]`
- 已验收原型 → `[已验收原型]`
- 多处说法并存 → 如实说分裂，不挑一个当事实

不假定读者记得前序会话的调查结论——哪怕上一轮刚查过，关键事实也要重新交代。

### 4. 数字具体化

- ❌ `最近经常失败`
- ✅ `过去 7 天有 12 笔订单出现这种情况`

### 5. 技术细节隔离

实现细节只放「技术备注」，不在正文打断业务叙述。正文读不懂时，读者不需要看技术备注也能行动。

## 禁止项（红线）

使用本 skill 的回复禁止出现：

- 未翻译的类名、函数名、文件名、模块名、服务名、API 路径、表名、依赖名、配置项、分支名、commit；
- 把调用链、数据结构、框架机制作为叙述主体；
- “收口”“主抽象”“冒烟”“契约”等内部黑话直接对外；
- 假设读者知道前序会话、仓库结构、spec 条款、代号；
- 用“代码里”“我刚才查到”开头但不给业务结论；
- 模糊事实，不标注证据来源；
- 只讲“怎么改”，不讲“对用户/业务有什么影响”。

技术模式下，内部标识符只允许出现在「技术备注」或用户明确要求的细节段，并保证正文仍可独立读懂；这不等于可以把未翻译的类名直接当叙述主体。

## 与 AGENTS.md 的关系

AGENTS.md 的「沟通对象」是身份契约（默认读者是谁、什么算合格）；本 skill 是它的展开细则（怎么翻译、用什么 Schema、怎么自检）。两者冲突时以 AGENTS.md 的身份契约为准。

## 与 decision-question 的关系

`decision-question` 专门管“待拍板问题”的写作，是决策场景的专用规范。本 skill 是默认的对外表述层。

- 输出里**没有**待拍板项 → 只用本 skill；
- 输出里**有**待拍板项 → 本 skill 的「需要你做什么」字段内部，必须套用 `decision-question` 的六段决策简报：请你定什么 → 这是什么 → 现状与发现 → 为什么需要你拍板 → 可选项 → 我的倾向。

## 反例与正例

**场景**：Agent 查到一个线上 bug——用户支付成功后页面仍显示失败，原因是支付回调重复到达时没有做去重。

❌ 反例（全是研发黑话，PM 无法行动）：

> 线上 `PaymentCallbackController` 收到重复回调时，`OrderService` 没有走幂等分支，导致 `order.status` 被覆盖成 `FAILED`。建议在 `PaymentCallbackService` 里加 `idempotency_key` 校验，失败返回 409。

✅ 正例：

> # 支付成功但页面显示失败的处理方案
>
> ## 一句话结论
> 少量用户会遇到已扣款但页面仍显示失败，需要定一个处理策略。
>
> ## 这是什么
> 用户在购物 App 提交订单并完成支付后，系统应该显示支付成功。现在支付渠道的确认消息偶尔会重复到达，系统没有正确识别“这已经是同一笔支付”，导致页面被改成失败状态。
>
> ## 现状与证据
> [已实现] 线上确实存在重复支付确认，且当前逻辑会把订单状态覆盖为失败；过去 7 天有 12 笔订单出现这种情况。
>
> ## 为什么重要
> 用户看到“支付失败”但钱已扣，会重复支付或找客服，影响信任和客服成本。
>
> ## 需要你做什么
> 请拍板：重复确认到达时，是直接忽略，还是向支付渠道再确认一次？
> - A. 直接忽略：处理快，风险低，但前提是首次确认一定可靠；
> - B. 再向渠道确认：更稳妥，但多一次外部请求，速度稍慢。
> 我的倾向：A——首次确认已经足够可靠，直接忽略最简单，也能避免用户侧延迟。
>
> ## 技术备注（研发核对用）
> `PaymentCallbackController` 收到重复回调时，`OrderService` 需按 `idempotency_key` 去重，重复请求返回 409，不覆盖 `order.status`。
