# Reflect — 跨会话记忆的反思与沉淀

## 这个 skill 做什么

会话结束后，扫描本轮对话，把"工作教我们的东西"沉淀成可跨会话复用的记忆。它解决的不是"把对话存下来"，而是"提炼出下一轮开工前该知道的洞察"。

两条区分是本 skill 的基石：

- **指令层 ≠ 记忆层**。AGENTS.md / spec / skill 是"开工前就知道、想让每轮都生效"的稳定指令；记忆是"干活过程中工作教会我们、开工前不知道"的东西。两者混在一起会让必读层膨胀、互相打架。本 skill 因此把落点分成两档（见 Step 2）。
- **日志 ≠ 反思 ≠ 记忆**。原始对话是日志（记录了什么）；反思是从中提炼"我当时要是早知道 X 就好了"（解释了什么）；记忆是把反思固化成可复用洞察（保留什么）。本 skill 做的是后两步，不是第一步。

记忆是经验性的"实然"，不是权威的"应然" spec。它可能在代码演进后失效，因此每条记忆都带一个**触发钩子**（下次什么情境下该读它）、证据与明确的**失效条件**（什么情况发生时本条就没用了），并在每次运行时顺带巡检清理已失效条目，绝不被当作每轮必读指令消费。

## 何时触发

- 手动：用户调用 `/reflect`，或表达"沉淀一下""回顾这轮对话""把值得记住的存下来""总结该记住的"。
- 当前版本仅手动触发，不在会话中自动运行，避免无人确认下写入记忆。

## 核心原则

1. **不制造第二套口径**。若反思发现的是 spec 矛盾、双线实现或已有规则的偏差，落点必须是"修正既有锚点（AGENTS.md / spec）"，而非新建一条平行记忆。这与仓库 AGENTS.md 的"单一事实源""spec 矛盾即阻断"一致。
2. **必读层只提案、不落盘**。任何对 AGENTS.md / spec / skill 的改动，先生成结构化提案等用户确认；只有可探索记忆层（memory/）才自动写入。
3. **记忆必须可匹配、可核验**。每条记忆带触发钩子（下次什么情境下该读）、证据引用（文件:行 或对话依据）和失效条件——"什么情况发生时本条就没用了"（如"seed 步骤被测试脚手架自动化"）。钩子决定读侧能否在正确时机想起它，必须包含读侧会持有的表面信号；失效条件要写得可判定，是后续读侧核验和运行时巡检的裁决依据。无据记忆不写。
4. **排除"本来就知道的"**。已写进 AGENTS.md / spec / skill 的内容不重复存为记忆。

## 工作流

### Step 1 — 反思扫描

扫描本轮对话，提取候选记忆。聚焦六类信号：

- **踩坑 / 卡点**：agent 反复碰壁、绕路、报错后才走通的点。
- **隐藏依赖**：不显眼但改动时必须同步处理的关联（如改 A 必须先做 B）。
- **被纠正的偏好**：用户纠正了 agent 的默认行为或输出。
- **已做决策及原因**：本轮拍板了某个取舍，以及为什么（避免下轮重审）。
- **开工前缺的关键事实**：本轮中途才弄清的、影响理解的环境/配置/边界信息。
- **可复用工具 / 脚本**：本轮编写或发现的高复用价值脚本（含写在 /tmp、heredoc 等不留痕位置、下轮会话会丢失的）。判断标准：换一个任务或会话是否仍可能用到；是则候选，纯一次性则排除。

排除：已在必读层中、属于通用常识、纯一次性临时上下文（如"本次先这样改"而无复用价值）。

### Step 2 — 分类路由

对每个候选判定三个维度，再落点：

- **稳定性**：稳定全局适用，还是偶发/情境？
- **适用范围**：user（个人偏好/行为） / project（仓库事实）？
- **是否需每轮可见**：每轮都该生效 → 必读层；相关时才需 → 可探索层。

路由矩阵：

| 候选性质 | 落点 | 当前动作 |
|---|---|---|
| 全局稳定行为规则 | `~/.agents/AGENTS.md`（用户级） | 仅提案 |
| 仓库稳定契约 / 架构 / 边界 | 仓库 `AGENTS.md` / `docs` 下 spec | 仅提案；收口入口为 spec-guide 场景 C，提案内容应可直接作为 C1 变更来源 |
| 复用流程 / 能力 | 对应 skill 文件 | 仅提案 |
| 可复用工具 / 脚本 | 合适既有 skill 的 `scripts/`；无承载 skill 时新建 skill | 仅提案，确认后经 skill-creator 落盘 |
| 偶发教训 / 隐藏依赖 / 情境事实 | 仓库 `memory/` | **自动写** |
| 实为题发现的 spec 矛盾 / 双线实现 | 修正既有 spec / AGENTS.md | 仅提案（禁新建平行记忆）；提案的唯一收口入口是 spec-guide 场景 C，不在 reflect 内直接改 spec |

作用域标签：即便全部记忆都入库，仍用 `user | project` 标签标记。`user` 级条目的唯一归宿是晋升到 `~/.agents/AGENTS.md`，因此必须在同一次 `/reflect` 内生成提案或降级为 `project`，不允许跨轮悬空（见 Step 5）。

### Step 3 — 生命周期巡检（无条件执行）

**无论本轮是否产生新记忆，每次 `/reflect` 必须执行本步。** 巡检是清扫已失效记忆的唯一主动时机，跳过巡检（如"本轮无可沉淀、直接结束"）会导致失效记忆持续堆积。读侧（project-entry 的 memory 读协议）在消费时发现失效只上报到 `memory/stale.md`，不直接删除；本步是唯一的删除入口。

0. **初始化检查**：运行 `python3 "$HOME/.agents/skills/reflect/scripts/reflect-memory.py" init`（默认向上探测仓库根）。仓库根不存在 `memory/` 时创建标准骨架——`memory/MEMORY.md`（索引，含说明 +「条目」区块 +「待确认提案」区块，**不含**格式标记）、`memory/stale.md`（读侧待清理队列）、`memory/inbox.md`（导入待补队列）、`memory/proposals/`（放 `.gitkeep` 占位）、五个空主题文件（各带一级标题）；`memory/` 已存在时只补齐缺失的 `MEMORY.md` / `proposals/` / 队列文件 / 标准主题文件，不改动已有内容。骨架的 `memory-schema` 标记由 Step 6 的 `certify` 写入——标记是认证的提交点，不由 `init` 预写。这样跨仓库首次 `/reflect` 也能开箱即用。
1. **失效识别**：运行 `python3 "$HOME/.agents/skills/reflect/scripts/reflect-memory.py" check`，获取机械信号——「证据文件已消失」的疑似失效条目、「索引与条目不一致」（索引是生成物，与条目渲染结果逐行比对）、「索引漂移 / 索引指向不存在的文件」、「失联提案」、「条目缺必填字段」、「字段重复」、「钩子含保留字符 `→`」、「疑似条目但无法解析的标题 / 非法主题文件名」、「锚点缺失 / 悬空 / 重复 / 日期或类型不匹配」、「索引区块或队列文件中有无法解析的行」、「未认证 / 格式版本高于当前技能」、「待清理队列非空 / 队列行目标已不存在」、「待补队列非空」。脚本信号只是提醒，不据此直接删除。
2. **待清理队列消费**：`check` 报 `memory/stale.md` 非空时，逐行处理——读代码复核该行证据仍成立后，删除目标条目与队列行，然后运行 `index` 重建索引（不要手改「条目」区块）；证据已不成立（读侧误判）则只删队列行，保留条目并说明原因；队列行指向的条目已不存在（孤立行）直接删队列行。队列是工作队列，不是归档区，处理后必须清空。行首日期是**读侧发现失效的日期**，不是条目捕获日；条目靠 `file#id` 定位，不要用日期去对条目。
3. **待补队列消费**：`check` 报 `memory/inbox.md` 非空时，逐行处理——能补齐触发 / 证据 / 失效条件并核验成立的，移入对应主题文件，运行 `index` 登记索引，删除 inbox 行；已过时的带证据删除；仍补不齐的保留并报告。inbox 是工作队列，不是归档区，不能当作可检索记忆。
4. **逐条裁决**：失效条件是否已触发，必须读代码确认，不依赖脚本信号。失效条件已触发的条目（无论是否命中脚本信号）当轮删除，随后运行 `index` 重建索引。失效即删，不设"归档区"，历史留存交给版本库。不按时间判断新旧：仓库久未改动不代表记忆失效，有效性只挂在代码状态上。
5. **提案残留清理**：脚本报「失联提案」信号（`proposals/` 下存在但索引"待确认提案"区块未列出的文件）时，这是裁决后未清理的残留，当轮与用户确认后删除；此为兜底，主机制仍是裁决当轮由执行落盘的一方删除。
6. **索引不一致修复**：脚本报「索引与条目不一致」或「索引漂移」时，不要逐行改索引——先确认条目无误，再运行 `index`（或 `certify`）重建；新增条目、悬空行、同日多行缺失都会在重建后自动对齐。索引是生成物，手改会立刻再次不一致。

### Step 4 — 沉淀到 memory/（自动写）

1. 读 `memory/MEMORY.md` 与可能相关的主题文件，去重 / 合并，不制造平行条目。**合并规则**：同主题的既有记忆与新候选合并时——失效条件取**并集**（任一触发即失效，宁可保守多删不可漏删）；证据合并为**列表**（保留原始与新增）；标题取更准确的一方或合并表述；内容取并集后去冗余。合并后更新「捕获于」为本次合并日期。合并本身视为该条目的更新事件，触发索引行同步更新。
2. **写入或更新主题文件**：优先用 `reflect-memory.py add <payload.json|->`——脚本校验字段齐全、类型 / 作用域取值、id 唯一性、钩子保留字符，写入前预演整文件形状，写入后自动重建索引。合并既有条目或需要改多行时可直接编辑条目，但不要手写索引。主题文件：`memory/dependencies.md`（隐藏依赖）、`memory/pitfalls.md`（踩坑）、`memory/decisions.md`（决策及原因）、`memory/preferences.md`（被纠正的偏好）、`memory/facts.md`（情境事实）。新主题按需新增：先建文件（如 `printf '# 测试\n' > memory/testing.md`）再 `add`；文件名必须是 memory/ 下的单段名称，不能含空白、路径分隔符、`#`、`→`，否则索引行无法解析。
3. **不要手写 `MEMORY.md` 的「条目」区块**：它是生成物，由 `reflect-memory.py index` / `certify` 从条目字段渲染。索引行格式：`- [类型] <YYYY-MM-DD> <钩子> → file.md#<id>`——钩子取条目的 `钩子` 字段，缺省回退 `触发`；条目地址是 `file#id`，日期是捕获日。钩子必须包含 1–3 个读侧真的会持有的表面信号（文件路径 / 符号 / 命令 / 报错串 / 模块名 / 用户措辞），能明确判定匹配或不匹配，不写"做设计时""改代码时"这类抽象类别；钩子内不能含 `→`（索引分隔符），`add` 会拒绝、`check` 会点名。索引整体控制在约 200 行内。「待确认提案」区块仍需手工维护，它不受索引生成影响。
4. 按下方"记忆条目格式"书写，带证据与失效条件。字段行必须从第 0 列开始；缩进行视为「内容」续行，不参与字段解析（多行「内容」因此可以安全包含 `- 类型: ...` 这类项目符号）。

### Step 5 — 必读层提案（仅提案，不落盘）

0. **user 级条目当轮收口**：Step 2 标为 `scope: user` 的条目，必须在同一次 `/reflect` 内二选一——生成必读层提案（进入下一步），或改写为 `scope: project`。不允许"标了 user 级、仍只存在项目记忆里"的悬空状态。生成提案后，原条目在裁决前保持 user 级并由索引「待确认提案」区块可见；裁决后按结果落盘，并同步降级为 `project` 或删除。
1. 对落在必读层的候选，写入 `memory/proposals/<YYYY-MM-DD>.md`，并在对话中给出精炼摘要，等用户确认后才落盘。
2. 提案格式见下方"必读层提案格式"。
3. **裁决即清理**：提案被裁决（采纳 / 部分采纳 / 否决）后，由执行落盘的一方当轮删除提案文件并移除 `MEMORY.md` 索引行。已采纳部分的事实源是落盘后的目标文件与版本库历史；部分采纳时未采纳部分视同否决，不留"部分落地"状态。否决理由若有复用价值，先沉淀为 `decisions.md` 决策记忆再删提案。
4. 若候选实为 spec 矛盾 / 双线实现：提案内容应为"修正既有锚点的具体 diff 建议"，而非新建记忆或新规则。
5. 若候选为可复用工具 / 脚本：提案必须包含脚本完整内容（或现有路径）、建议落点（哪个既有 skill 的 `scripts/`，附归属理由；无承载 skill 时说明新建 skill 的职责定位），用户确认后调用 skill-creator 执行落盘——reflect 不直接写 skill 文件，skill 的新建/修改规范由 skill-creator 承载。
6. 注意：agent 对 `memory/` 的感知由 project-entry skill 承载——它已声明 memory/ 的存在判据（不存在属正常、禁止主动创建）与消费纪律（按需读、用前核验）。仓库级 AGENTS.md 无需再单独添加指向说明。

### Step 6 — 认证（形状合规时）

完成本轮写入后，运行 `python3 "$HOME/.agents/skills/reflect/scripts/reflect-memory.py" certify`。它先校验条目形状，通过后**重建 `MEMORY.md` 的「条目」区块**，再做锚点 / 证据 / 队列校验，最后写入 `<!-- memory-schema: 3 -->` 标记；有阻断则列出阻断项并拒绝写入（条目形状不合法时不会改动索引）。

阻断项：缺 `MEMORY.md`、标记无法识别或高于当前版本、条目缺必填字段、字段重复、钩子含 `→`、疑似条目但无法解析的标题、主题文件名含空白 / 路径分隔符 / `#` / `→`、索引区块内有无法解析的行、索引漂移、索引指向不存在文件、证据文件消失、锚点缺失 / 悬空 / 重复 / 日期或类型不匹配、队列文件有无法解析的行。待清理队列 / 待补队列**非空**不阻断认证——标记认证的是活动索引的形状，不是队列的清空状态；但队列里出现**无法解析的行**会阻断（包括漏写 `-`、以日期开头的行），那意味着读侧的失效上报可能已被静默丢弃。

禁止手写标记绕过认证。标记为 older、或认证报缺 `id` / 锚点问题时，按 `references/memory-conversion.md` 的「v2 → v3 迁移」处理后再认证。

## 导入模式（其他格式 → 当前格式）

触发：用户说“把 X 的记忆导进来”，或调用 `/reflect --import <path>`。仅手动触发，不自动扫描。

权威作业指导书：`references/memory-conversion.md`（目标契约、源范围、准入/路由、字段映射、inbox、备份、批量与报告）。本文件只写入口与不可省略的硬约束。

硬约束：

1. 先读 `references/memory-conversion.md`，按管线执行；不凭印象搬运。
2. 改写目标 `memory/` 前必须备份（git 或整目录快照）；两者都不可用则中止报告。
3. 源文件只读；来源路径与行号写进证据字段。
4. 不伪造触发 / 证据 / 失效条件；推不出的条目写入 `memory/inbox.md`，不进主题文件与索引。
5. `scope: user` 导入时默认降级为 project；通用候选合成一份必读层提案。
6. 单批 20–30 条，逐批 `check`；全部完成后运行 `certify` 写合规标记。认证失败不手写标记。
7. 报告按 imported / merged / skipped / needs-decision 四类逐条列出。

导入不是“把旧文件改写成新字段”，而是按目标准入标准重新提炼；日志、任务状态、临时笔记不进入记忆。

## 脚本命令

```
reflect-memory.py init       [repo_root]                  # 建/补骨架
reflect-memory.py check      [repo_root]                  # 只读体检
reflect-memory.py certify    [repo_root]                  # 重建索引 → 校验 → 写标记
reflect-memory.py index      [repo_root]                  # 只重建索引
reflect-memory.py add        <payload.json|-> [repo_root] # 写一条记忆（自动重建索引）
reflect-memory.py stale-add  <payload.json|-> [repo_root] # 追加待清理队列
reflect-memory.py inbox-add  <payload.json|-> [repo_root] # 追加待补队列
reflect-memory.py schema                                  # 输出机器可读格式契约
```

写入走 payload（JSON 文件或 stdin）而不是手写 markdown：手写产生的格式变体会被持久化、并被解析器静默接受；payload 解析失败则在落盘前拒绝，可当场重试。所有写命令共用一条不变量：**写出的行必须能被对应解析器读回**——`add` / `stale-add` / `inbox-add` 落盘前先自校验，`add` 还会预演整文件形状，失败一律不落盘。`add` 的键可用中文或英文别名（`type` / `类型`、`trigger` / `触发` 等），必填 `file`、`主题`、`id`、`类型`、`作用域`、`触发`、`证据`、`失效条件`、`内容`，`钩子` 可选。字段与行格式的单一来源是 `reflect-memory.py schema` 的输出，本文档不复述全部约束。

## 存储布局

## 记忆条目格式

每条写入主题文件的记忆：

```markdown
## <YYYY-MM-DD> — <一句话主题>

- id: <短 ASCII slug；同文件内唯一；索引行用 file#id 指向它>
- 类型: 隐藏依赖 | 踩坑 | 决策 | 偏好 | 情境事实
- 作用域: user | project
- 钩子: <可选；索引行用的短钩子，缺省回退「触发」；不能含 →>
- 触发: <下次什么任务/现象下应该读这条；1–3 个读侧会持有的表面信号，如文件路径、符号、命令、报错串、用户措辞>
- 证据: <文件:行 或 本轮对话中的依据>
- 捕获于: <YYYY-MM-DD>
- 失效条件: <什么情况发生时本条失效，要可判定，如"seed 步骤被测试脚手架自动化">
- 内容: <可复用洞察——what 与 why，简洁具体>
```

**触发与失效条件是一对**：触发是读的守卫（什么时候该打开），失效条件是信的守卫（什么时候不再可信）。只写结论不写触发，读侧就无法在对的时候想起它。

**钩子只写一次**：`钩子` 是索引行用的短句，`触发` 是条目内的完整描述。索引从 `钩子` 生成，不需要在索引里再写一遍；缺省回退 `触发`，索引行会变长——条目多时建议显式写 `钩子`。

**id 是地址，不是标题的复制**：取短 ASCII slug，同文件内唯一；改标题不强制改 id，除非条目语义变了。索引行必须用 `file#id` 指向它，锚点缺失或悬空都会被 `check` 点名。

**标题日期 = 捕获日期**：标题里的 `<YYYY-MM-DD>` 必须与「捕获于」字段一致，统一取记忆写入当天的日期，禁用"事件发生日"。一条洞察可能在事件发生多日后才被复盘沉淀，用捕获日做主键，避免事后补写时两个日期字段分裂、后续无法对齐。

示例：

```markdown
## 2026-07-13 — notification 集成测试需先 seed

- id: notification-seed
- 类型: 隐藏依赖
- 作用域: project
- 钩子: 跑 notification 集成测试 / 审计事件映射报错时
- 触发: 跑 notification 集成测试；或审计事件映射测试因缺 fixture 失败时
- 证据: apps/editor/src/lib/audit-events.ts:42；本轮 pnpm test 失败后经排查发现
- 捕获于: 2026-07-13
- 失效条件: seed 步骤被测试脚手架自动化，集成测试不再需要手动 seed
- 内容: 改 notification 偏好相关逻辑后跑集成测试，必须先 `pnpm seed:test-notifications`，否则审计事件映射测试会因缺 fixture 失败。

对应索引行（由 `certify` / `index` 生成，不要手写；钩子不复述结论，`file#id` 定位条目）：

- [隐藏依赖] 2026-07-13 跑 notification 集成测试 / 审计事件映射报错时 → dependencies.md#notification-seed
```

## 必读层提案格式

```markdown
# 必读层提案 <YYYY-MM-DD>

## 提案 N — <一句话>
- 目标文件: <~/.agents/AGENTS.md | 仓库 AGENTS.md | docs/.../spec.md | skills/...>
- 改动类型: 新增规则 | 修正矛盾 | 删除旧口径
- 建议 diff:
  ```diff
  + 新增/修改的行
  - 删除的行
  ```
- 依据: <本轮对话中的证据>
- 理由: <为什么该进必读层而非记忆层>

> 本文件在裁决（采纳 / 部分采纳 / 否决）后由执行落盘的一方删除，并移除 `MEMORY.md` 索引对应行。
```

## 禁止事项

- 禁止自动改写 AGENTS.md / spec / skill——必读层改动只出提案。
- 禁止为已存在于必读层的内容新建平行记忆。
- 禁止写入无证据、纯推测的记忆（每条必须带证据引用）。
- 禁止把"本来就知道的指令"当记忆存。
- 禁止把记忆当权威 spec 消费——下游使用前必须按失效条件核验。
- 禁止把失效条目留在文件中做"归档"标记——失效即删，历史留存交给版本库。
- 禁止裁决后残留提案文件——采纳、部分采纳、否决均当轮删除；否决理由有复用价值时先沉淀为 `decisions.md` 决策记忆。
- 禁止在索引行复述结论——索引只写触发钩子，结论留在主题文件条目里。
- 禁止索引行不带条目锚点 `file#id`——锚点是唯一定位，钩子只是检索线索。
- 禁止手写或局部编辑 `MEMORY.md` 的「条目」区块——它是生成物，改条目后运行 `index` 或 `certify` 重建。
- 禁止在 `stale.md` / `inbox.md` 里写自然语言或自创格式——解析不了的行过去会被静默丢弃，现在会阻断认证，但仍不要产生它们。
- 禁止让 `scope: user` 的条目留在项目记忆里跨轮悬空——当轮必须晋升为提案或降级为 `project`。
- 禁止在读侧直接删除或改写记忆条目——读侧只向 `memory/stale.md` 追加待清理记录，删除统一由本 skill 执行。
- 禁止导入时伪造触发 / 证据 / 失效条件——推不出就进 `memory/inbox.md`。
- 禁止删除或改写源记忆文件——导入只读源，只写目标 `memory/`。
- 禁止手写 `memory-schema` 标记绕过 `certify`。

## 已知限制（过期识别覆盖面）

本 skill 的失效识别不是全主动的。明确声明以下限制，避免下游误以为"有 memory/ 就高枕无忧"：

1. **只机械检测一种失效模式**：`check` 的失效信号只有“证据引用的文件已消失”一类；其余信号（索引不一致、锚点、队列、格式）都是形状与一致性检查，不判断记忆是否失效。最常见的失效模式——**语义/行为变化**（如"seed 步骤被自动化"导致旧记忆无意义、但证据文件还在）——脚本检测不到，因为失效条件挂在行为状态上，不挂在文件存在性上。

2. **只认带行号标注的证据引用**：`check` 提取的是 `path:12` 与 `path 第 12 行` 两种写法。证据写成裸路径（`server/index.mjs`）、URL 里的路径、或把文件名当反例的表述（"app/、server.js 均已删除"）都不在覆盖内——这是刻意的精度取舍：放宽为可选后曾在一个仓库一次产生 12 条误报（反例表述、`/files/../x.mjs` 这类 URL 路径、`.md` 这类选择器全被当成失效文件），噪声直接淹没信号。写证据时若想让某条记忆可被机械核验，就带上 `文件:行`。

3. **对话依据型证据无法机械校验**：证据字段为"本轮对话中的依据"（不含文件路径）的记忆，`check` 脚本无法提取任何路径，完全不在失效检测覆盖范围内。这类记忆的失效识别 100% 依赖读取时人工核验。

4. **巡检仅在手动 `/reflect` 时触发**：日常代码变更不会自动触发清扫，失效记忆会持续存在直到下次 `/reflect`（当前版本的取舍，见"何时触发"）。

5. **兜底依赖读取时核验**：鉴于以上限制，最后一道防线是 project-entry 的 memory 读协议——**消费任意记忆条目前，必须当轮重新确认失效条件未触发**，不能因"记忆已存在"就默认有效。这条是硬约束，不是建议。读侧发现失效时写入 `memory/stale.md` 待清理队列，发现因此不会随会话结束蒸发；但删除仍要等下一次 `/reflect`，及时性没有因此提高。

6. **导入质量依赖 agent 判断**：`certify` 只证明形状合规（字段齐全、索引对齐、证据文件存在），不证明内容正确或触发钩子写得好；这些仍由读侧消费前核验和用户抽查保证。

未来若需更强的及时性（事件驱动清扫），需引入 git 钩子或定期提醒，超出当前版本范围。

## 示例（一次 /reflect 的运行）

输入：本轮对话中，agent 改了通知偏好逻辑，跑 `pnpm test` 报审计事件映射失败，排查后发现需先 `pnpm seed:test-notifications`；另外用户纠正 agent"不要默认用 npm，本仓库一律 pnpm"。

产出：

1. `memory/dependencies.md` 自动新增一条"notification 集成测试需先 seed"的记忆（如上格式）。
2. `memory/preferences.md` 自动新增一条"本仓库一律 pnpm，勿用 npm"的偏好记忆，作用域 `user`。
3. `memory/proposals/2026-07-13.md` 生成一条提案：建议把"本仓库统一用 pnpm"从记忆晋升为用户级 `~/.agents/AGENTS.md` 的稳定规则（因属全局稳定行为，且已出现第二次）。摘要显示在对话中，等用户确认后落盘。
