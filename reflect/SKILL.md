# Reflect — 跨会话记忆的反思与沉淀

## 这个 skill 做什么

会话结束后，扫描本轮对话，把"工作教我们的东西"沉淀成可跨会话复用的记忆。它解决的不是"把对话存下来"，而是"提炼出下一轮开工前该知道的洞察"。

两条区分是本 skill 的基石：

- **指令层 ≠ 记忆层**。AGENTS.md / spec / skill 是"开工前就知道、想让每轮都生效"的稳定指令；记忆是"干活过程中工作教会我们、开工前不知道"的东西。两者混在一起会让必读层膨胀、互相打架。本 skill 因此把落点分成两档（见 Step 2）。
- **日志 ≠ 反思 ≠ 记忆**。原始对话是日志（记录了什么）；反思是从中提炼"我当时要是早知道 X 就好了"（解释了什么）；记忆是把反思固化成可复用洞察（保留什么）。本 skill 做的是后两步，不是第一步。

记忆是经验性的"实然"，不是权威的"应然" spec。它可能在代码演进后失效，因此每条记忆都带证据与明确的失效条件（什么情况发生时本条就没用了），并在每次运行时顺带巡检清理已失效条目，绝不被当作每轮必读指令消费。

## 何时触发

- 手动：用户调用 `/reflect`，或表达"沉淀一下""回顾这轮对话""把值得记住的存下来""总结该记住的"。
- 当前版本仅手动触发，不在会话中自动运行，避免无人确认下写入记忆。

## 核心原则

1. **不制造第二套口径**。若反思发现的是 spec 矛盾、双线实现或已有规则的偏差，落点必须是"修正既有锚点（AGENTS.md / spec）"，而非新建一条平行记忆。这与仓库 AGENTS.md 的"单一事实源""spec 矛盾即阻断"一致。
2. **必读层只提案、不落盘**。任何对 AGENTS.md / spec / skill 的改动，先生成结构化提案等用户确认；只有可探索记忆层（memory/）才自动写入。
3. **记忆必须可核验**。每条记忆带证据引用（文件:行 或对话依据）和失效条件——"什么情况发生时本条就没用了"（如"seed 步骤被测试脚手架自动化"）。失效条件要写得可判定，是后续读侧核验和运行时巡检的裁决依据。无据记忆不写。
4. **排除"本来就知道的"**。已写进 AGENTS.md / spec / skill 的内容不重复存为记忆。

## 工作流

### Step 1 — 反思扫描

扫描本轮对话，提取候选记忆。聚焦六类信号：

- **踩坑 / 卡点**：agent 反复碰壁、绕路、报错后才走通的点。
- **隐藏依赖**：不显眼但改动时必须同步处理的关联（如改 A 必须先做 B）。
- **被纠正的偏好**：用户纠正了 agent 的默认行为或输出。
- **已做决策及原因**：本轮拍板了某个取舍，以及为什么（避免下轮重审）。
- **开工前缺的关键事实**：本轮中途才弄清的、影响理解的环境/配置/边界信息。
- **可复用工具 / 脚本**：本轮编写或发现的高复用价值脚本（含写在 /tmp、heredoc 等不留痕位置、下轮会话会丢失的）。判断标准：换一个任务或会话是否仍可能用到；是则候选，纯一次性则排除。

排除：已在必读层中、属于通用常识、纯一次性临时上下文（如"本次先这样改"而无复用价值）。

### Step 2 — 分类路由

对每个候选判定三个维度，再落点：

- **稳定性**：稳定全局适用，还是偶发/情境？
- **适用范围**：user（个人偏好/行为） / project（仓库事实）？
- **是否需每轮可见**：每轮都该生效 → 必读层；相关时才需 → 可探索层。

路由矩阵：

| 候选性质 | 落点 | 当前动作 |
|---|---|---|
| 全局稳定行为规则 | `~/.agents/AGENTS.md`（用户级） | 仅提案 |
| 仓库稳定契约 / 架构 / 边界 | 仓库 `AGENTS.md` / `docs` 下 spec | 仅提案；收口入口为 spec-guide 场景 C，提案内容应可直接作为 C1 变更来源 |
| 复用流程 / 能力 | 对应 skill 文件 | 仅提案 |
| 可复用工具 / 脚本 | 合适既有 skill 的 `scripts/`；无承载 skill 时新建 skill | 仅提案，确认后经 skill-creator 落盘 |
| 偶发教训 / 隐藏依赖 / 情境事实 | 仓库 `memory/` | **自动写** |
| 实为题发现的 spec 矛盾 / 双线实现 | 修正既有 spec / AGENTS.md | 仅提案（禁新建平行记忆）；提案的唯一收口入口是 spec-guide 场景 C，不在 reflect 内直接改 spec |

作用域标签：即便全部记忆都入库，仍用 `user | project` 标签标记。user 级事实未来若晋升，目标是 `~/.agents/AGENTS.md`。

### Step 3 — 生命周期巡检（无条件执行）

**无论本轮是否产生新记忆，每次 `/reflect` 必须执行本步。** 巡检是清扫已失效记忆的唯一主动时机，跳过巡检（如"本轮无可沉淀、直接结束"）会导致失效记忆持续堆积。除本步的 `/reflect` 集中清扫外，读侧（project-entry 的 memory 读协议）在消费记忆时发现失效也会即时删除——两条路径互补，本步是兜底性的全量清扫。

0. **初始化检查**：运行 `python3 "$HOME/.agents/skills/reflect/scripts/reflect-memory.py" init`。当前仓库（工作目录）下不存在 `memory/` 时创建标准骨架——`memory/MEMORY.md`（索引，含"经验性记忆、非权威 spec、按需读取并按失效条件核验"的说明 +「条目」区块 +「待确认提案」区块）、`memory/proposals/`（放 `.gitkeep` 占位）、五个空主题文件（各带一级标题）；已存在则不改动。这样跨仓库首次 `/reflect` 也能开箱即用。
1. **失效识别**：运行 `python3 "$HOME/.agents/skills/reflect/scripts/reflect-memory.py" check`，获取机械信号——「证据文件已消失」的疑似失效条目、「索引漂移」（主题文件条目与索引条目按「日期 + 指向文件」多重集比对，可检出漏登/悬空/跨主题文件错指/指向文件不存在）、「失联提案」。脚本信号只是提醒，不据此直接删除。
2. **逐条裁决**：失效条件是否已触发，必须读代码确认，不依赖脚本信号。失效条件已触发的条目（无论是否命中脚本信号）当轮删除，并同步清理 `MEMORY.md` 索引对应行。失效即删，不设"归档区"，历史留存交给版本库。不按时间判断新旧：仓库久未改动不代表记忆失效，有效性只挂在代码状态上。
3. **提案残留清理**：脚本报「失联提案」信号（`proposals/` 下存在但索引"待确认提案"区块未列出的文件）时，这是裁决后未清理的残留，当轮与用户确认后删除；此为兜底，主机制仍是裁决当轮由执行落盘的一方删除。
4. **索引漂移修复**：脚本报「索引漂移」时，当轮对齐——主题文件新增了条目就补索引行，索引有悬空就补条目或删索引行；报「跨主题文件错指」时改正索引行的 `→ 文件` 字段。比对按多重集，所以同日多行时"多一行/少一行"都会被报出，不要只核对该日期是否出现过。

### Step 4 — 沉淀到 memory/（自动写）

1. 读 `memory/MEMORY.md` 与可能相关的主题文件，去重 / 合并，不制造平行条目。**合并规则**：同主题的既有记忆与新候选合并时——失效条件取**并集**（任一触发即失效，宁可保守多删不可漏删）；证据合并为**列表**（保留原始与新增）；标题取更准确的一方或合并表述；内容取并集后去冗余。合并后更新「捕获于」为本次合并日期。合并本身视为该条目的更新事件，触发索引行同步更新。
2. 写入或更新对应主题文件：`memory/dependencies.md`（隐藏依赖）、`memory/pitfalls.md`（踩坑）、`memory/decisions.md`（决策及原因）、`memory/preferences.md`（被纠正的偏好）、`memory/facts.md`（情境事实）。新主题按需新增。
3. **维护 `memory/MEMORY.md` 索引**：简洁、指向主题文件、控制在约 200 行内；细节留在主题文件，不堆进索引。索引条目的主题句必须包含可检索关键词（模块名 / 命令 / 错误特征），保证读侧按用户级规则的触发时刻扫索引时能识别相关性——记忆的可发现性是写侧的责任。索引行格式：`- [类型] <YYYY-MM-DD> 主题句 → file.md`——**日期是稳定主键**，必须与主题文件条目标题 `## YYYY-MM-DD — 主题` 的日期一致（标题日期即捕获日期，见"记忆条目格式"）。`reflect-memory.py check` 按「日期 + 指向文件」多重集做双向关联：同一天可有多个条目（分属不同主题文件），因此**同日多行是正常的，行数必须与对应主题文件的条目数逐一对上**——多一行即悬空，少一行即漏登；索引行指向的主题文件写错也会被报出（照索引去该文件找不到条目）。主题句措辞可与标题不同（一个是检索摘要、一个是标题，允许异文）。索引须保留"待确认提案"区块，列出 `proposals/` 下未确认的提案（日期 + 一句话主题），确认或否决后移除索引行并删除对应提案文件——提案是索引下唯一需要主动浮出水面的产物。
4. 按下方"记忆条目格式"书写，带证据与失效条件。

### Step 5 — 必读层提案（仅提案，不落盘）

1. 对落在必读层的候选，写入 `memory/proposals/<YYYY-MM-DD>.md`，并在对话中给出精炼摘要，等用户确认后才落盘。
2. 提案格式见下方"必读层提案格式"。
3. **裁决即清理**：提案被裁决（采纳 / 部分采纳 / 否决）后，由执行落盘的一方当轮删除提案文件并移除 `MEMORY.md` 索引行。已采纳部分的事实源是落盘后的目标文件与版本库历史；部分采纳时未采纳部分视同否决，不留"部分落地"状态。否决理由若有复用价值，先沉淀为 `decisions.md` 决策记忆再删提案。
4. 若候选实为 spec 矛盾 / 双线实现：提案内容应为"修正既有锚点的具体 diff 建议"，而非新建记忆或新规则。
5. 若候选为可复用工具 / 脚本：提案必须包含脚本完整内容（或现有路径）、建议落点（哪个既有 skill 的 `scripts/`，附归属理由；无承载 skill 时说明新建 skill 的职责定位），用户确认后调用 skill-creator 执行落盘——reflect 不直接写 skill 文件，skill 的新建/修改规范由 skill-creator 承载。
6. 注意：agent 对 `memory/` 的感知由 project-entry skill 承载——它已声明 memory/ 的存在判据（不存在属正常、禁止主动创建）与消费纪律（按需读、用前核验）。仓库级 AGENTS.md 无需再单独添加指向说明。

```
memory/
  MEMORY.md            # 索引（可探索，按需读，非每轮必读）—— 含「条目」区块（主题句+指向）与「待确认提案」区块
  dependencies.md      # 隐藏依赖

  decisions.md         # 决策及原因
  preferences.md       # 被纠正的偏好
  facts.md             # 情境事实
  proposals/           # 必读层修改提案（待用户确认，裁决后即删）

```

## 记忆条目格式

每条写入主题文件的记忆：

```markdown
## <YYYY-MM-DD> — <一句话主题>

- 类型: 隐藏依赖 | 踩坑 | 决策 | 偏好 | 情境事实
- 作用域: user | project
- 证据: <文件:行 或 本轮对话中的依据>
- 捕获于: <YYYY-MM-DD>
- 失效条件: <什么情况发生时本条失效，要可判定，如"seed 步骤被测试脚手架自动化">
- 内容: <可复用洞察——what 与 why，简洁具体>
```

**标题日期 = 捕获日期**：标题里的 `<YYYY-MM-DD>` 必须与「捕获于」字段一致，统一取记忆写入当天的日期，禁用"事件发生日"。一条洞察可能在事件发生多日后才被复盘沉淀，用捕获日做主键，避免事后补写时两个日期字段分裂、后续无法对齐。

示例：

```markdown
## 2026-07-13 — notification 集成测试需先 seed

- 类型: 隐藏依赖
- 作用域: project
- 证据: apps/editor/src/lib/audit-events.ts:42；本轮 pnpm test 失败后经排查发现
- 捕获于: 2026-07-13
- 失效条件: seed 步骤被测试脚手架自动化，集成测试不再需要手动 seed
- 内容: 改 notification 偏好相关逻辑后跑集成测试，必须先 `pnpm seed:test-notifications`，否则审计事件映射测试会因缺 fixture 失败。
```

## 必读层提案格式

```markdown
# 必读层提案 <YYYY-MM-DD>

## 提案 N — <一句话>
- 目标文件: <~/.agents/AGENTS.md | 仓库 AGENTS.md | docs/.../spec.md | skills/...>
- 改动类型: 新增规则 | 修正矛盾 | 删除旧口径
- 建议 diff:
  ```diff
  + 新增/修改的行
  - 删除的行
  ```
- 依据: <本轮对话中的证据>
- 理由: <为什么该进必读层而非记忆层>

> 本文件在裁决（采纳 / 部分采纳 / 否决）后由执行落盘的一方删除，并移除 `MEMORY.md` 索引对应行。
```

## 禁止事项

- 禁止自动改写 AGENTS.md / spec / skill——必读层改动只出提案。
- 禁止为已存在于必读层的内容新建平行记忆。
- 禁止写入无证据、纯推测的记忆（每条必须带证据引用）。
- 禁止把"本来就知道的指令"当记忆存。
- 禁止把记忆当权威 spec 消费——下游使用前必须按失效条件核验。
- 禁止把失效条目留在文件中做"归档"标记——失效即删，历史留存交给版本库。
- 禁止裁决后残留提案文件——采纳、部分采纳、否决均当轮删除；否决理由有复用价值时先沉淀为 `decisions.md` 决策记忆。

## 已知限制（过期识别覆盖面）

本 skill 的失效识别不是全主动的。明确声明以下限制，避免下游误以为"有 memory/ 就高枕无忧"：

1. **只机械检测一种失效模式**：`check` 脚本只能识别"证据引用的文件已消失"和"索引漂移"两类信号。最常见的失效模式——**语义/行为变化**（如"seed 步骤被自动化"导致旧记忆无意义、但证据文件还在）——脚本检测不到，因为失效条件挂在行为状态上，不挂在文件存在性上。

2. **只认带行号标注的证据引用**：`check` 提取的是 `path:12` 与 `path 第 12 行` 两种写法。证据写成裸路径（`server/index.mjs`）、URL 里的路径、或把文件名当反例的表述（"app/、server.js 均已删除"）都不在覆盖内——这是刻意的精度取舍：放宽为可选后曾在一个仓库一次产生 12 条误报（反例表述、`/files/../x.mjs` 这类 URL 路径、`.md` 这类选择器全被当成失效文件），噪声直接淹没信号。写证据时若想让某条记忆可被机械核验，就带上 `文件:行`。

3. **对话依据型证据无法机械校验**：证据字段为"本轮对话中的依据"（不含文件路径）的记忆，`check` 脚本无法提取任何路径，完全不在失效检测覆盖范围内。这类记忆的失效识别 100% 依赖读取时人工核验。

4. **巡检仅在手动 `/reflect` 时触发**：日常代码变更不会自动触发清扫，失效记忆会持续存在直到下次 `/reflect`（当前版本的取舍，见"何时触发"）。

5. **兜底依赖读取时核验**：鉴于以上限制，最后一道防线是 project-entry 的 memory 读协议——**消费任意记忆条目前，必须当轮重新确认失效条件未触发**，不能因"记忆已存在"就默认有效。这条是硬约束，不是建议。

未来若需更强的及时性（事件驱动清扫），需引入 git 钩子或定期提醒，超出当前版本范围。

## 示例（一次 /reflect 的运行）

输入：本轮对话中，agent 改了通知偏好逻辑，跑 `pnpm test` 报审计事件映射失败，排查后发现需先 `pnpm seed:test-notifications`；另外用户纠正 agent"不要默认用 npm，本仓库一律 pnpm"。

产出：

1. `memory/dependencies.md` 自动新增一条"notification 集成测试需先 seed"的记忆（如上格式）。
2. `memory/preferences.md` 自动新增一条"本仓库一律 pnpm，勿用 npm"的偏好记忆，作用域 `user`。
3. `memory/proposals/2026-07-13.md` 生成一条提案：建议把"本仓库统一用 pnpm"从记忆晋升为用户级 `~/.agents/AGENTS.md` 的稳定规则（因属全局稳定行为，且已出现第二次）。摘要显示在对话中，等用户确认后落盘。
