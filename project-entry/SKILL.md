# 项目入口与文档地图（project-entry）

## 入口顺序

- 进入具体项目后，先读项目根 `AGENTS.md`（仓库级轻入口），理解仓库级规则与阅读原则。
- 详细任务路由、文档分发关系与定义优先级，按需读取 `docs/agent-map.yaml`；它是按需加载材料，不得形成第二套 spec 定义。
- 进入实现前，必须已读取与任务相关的 primary spec 基准。相关 spec 的发现顺序（每层缺失自动下落一层）：
  1. `docs/agent-map.yaml` 的 `routes`（有则按任务模式匹配必读清单）；
  2. `python3 "$HOME/.agents/skills/spec-guide/scripts/design_lint.py" --list-artifacts docs --root .`（派生索引，一次看全产物与状态）；
  3. 约定目录结构（`docs/spec/`、`docs/adr/` 等）；
  4. 全文检索（术语 / grep）。

## memory/ 读协议

仓库根存在 `memory/` 目录时，它是 reflect 沉淀的经验性记忆库（可探索、非必读，内容为实际经验、用前须按条目失效条件确认仍成立）。以下时刻必须先扫一遍 `memory/MEMORY.md` 索引——只读索引，命中主题再深入对应主题文件：

- 进入仓库开工
- 开始排查异常/报错
- 改动不熟悉的模块前
- 做技术决策/取舍前
- 用户提及"之前/以前"的经历时

规则：

- 索引无相关条目则直接跳过，不视为阻塞。
- 扫索引时若发现"待确认提案"区块非空，主动提醒用户有提案待拍板，拍板前不得自行落盘必读层改动；拍板（采纳 / 部分采纳 / 否决）后由执行落盘的一方（reflect 或用户）删除对应提案文件并移除索引行，已落盘内容以目标文件与版本库历史为准。
- **消费前核验是硬约束**：深入读取任意一条记忆条目、准备据此行动前，必须当轮重新确认该条目的失效条件未触发——读代码或核实现状，证实"what 与 why"仍然成立。这是事前核验，不是事后补救。原因：reflect 的失效识别只机械覆盖"证据文件消失"一种模式，语义/行为变化型失效（最常见）不会被自动检测，巡检也只在手动 `/reflect` 时触发（详见 reflect 的「已知限制」）。因此"记忆已存在于 memory/"不等于"记忆仍有效"，每次消费都必须独立核验。
- 核验后发现失效条件已触发：不以该记忆为依据行动，记录条目位置与失效证据，转 reflect skill 执行删除与索引清理；本 skill 不改写 `memory/`。
- 记忆与代码 / spec 冲突时以代码和 spec 为准。
- 仓库根不存在 `memory/` 属正常状态（该项目尚未运行过 reflect），不视为缺失，禁止主动创建——初始化由 reflect 首次运行时完成。

## 边界（Do NOT）

- 不写入记忆（归 reflect）；本 skill 只读，发现失效条目只报告并转 reflect 处理。
- 不重复「基本判断链」骨架与 spec 体系路由（design-guide / spec-guide）。
