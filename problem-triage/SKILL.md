# 问题分诊（problem-triage）

对应 user 级规则「基本判断链」：异常和报错只是入口，不是根因。禁止只看报错最后一行就补丁式修改。

## 入口

先完成「基本判断链」骨架：0 层级路由 → 1 定性 → 2 归属 → 3 裁定 → 4 收尾（骨架常驻 AGENTS.md）。
本 skill 承载骨架之下的两类深水区细则：**什么时候必须停补丁改重构**、**怎么对待用户给的具体实例**。

## 动手前的两个定位

打补丁或开新坑之前先完成两个定位。它们防的不是判断错误，而是"在错误的落点上做正确的修复"——症状在 A 处出现，补丁打在 B 处，根因从未被定位，于是同一问题以多轮补丁、多份计划的形式反复出现。

1. **落点验证**：修改配置、契约、构建、入口类文件前，先确认它真实的消费方（哪条构建链引用它、哪个入口 import 它、哪条 pipeline 执行它）——通常一条 grep / 引用链即可确认。消费链查不到时，该文件很可能是迁移遗留或被取代副本（幽灵产物），在它上面修复不会让症状消失。此时停止修改，把"疑似幽灵产物"作为发现报告用户裁决，而不是继续打补丁。
2. **同主题检索**：新开 plan、spec、守卫脚本或工具前，先检索仓库是否已有同主题锚点（文档索引/map、既有计划、既有守卫列表）。命中则回到既有锚点修订，不开新坑。理由：同一架构债被多个"新计划"反复局部重攻，会制造"一直在处理"的假象，比不修更难收口。

## 该停下补丁、改做重构的信号

出现以下任一信号时，默认当前问题是架构/契约的系统性裂缝，必须停止打补丁，主动把重构方案提交给用户拍板：

1. 同一节 spec/设计文档在短期内被反复修订，每次都是局部修补而非结构性决策。
2. 同类问题（如状态不一致、数据丢失、重复触发、并发竞态）以不同形态反复爆出。
3. 修 A 又破坏 B；或强约束路径（关键链路、硬守卫、核心契约）反而比弱约束路径（降级、兜底、容错）表现更差——典型的规矩对内外不一样。
4. 补丁向防护层蔓延：软约束（注释、prompt、文档约定）→ 代码层硬校验 → 多道硬校验叠加，每道守卫只为堵前一道的漏。
5. 局部修法要同步改 B/C/D 且改动仍在蔓延，代价已超过重构主抽象。

## 命中信号后的强制流程

停止打补丁 → 自查根因归属（定位到主抽象、契约或状态所有权，不是具体文件/函数）→ 给出 2-3 个重构方向（含局部修法作为对照），让用户拍板深度。

- 重构成功的标志是设计文档越改越薄；若变更厚，说明是更大规模的补丁而非重构。
- 用户偏好：默认「长久收益最高优先」，而非「最小改动优先」。

## 具体实例是样例，不是边界

用户用具体对象、具体文件、具体报错或具体场景描述问题时，不得默认把该实例视为修复范围。具体实例优先视为问题样例，按顺序处理：

1. 样例识别：是范围限定，还是用于举例说明问题。
2. 抽象归属：实例属于哪个主抽象、契约、状态所有权或数据管道。
3. 同类影响：同类对象、同一构建路径、同一消费路径是否存在相同风险。
4. 修复位置：优先修正主抽象或主契约；禁止只在样例附近打补丁。
5. 样例回归验证：具体实例必须作为验证样例之一。

用户明确使用"只修这个""仅处理这个实例""不要扩大范围"等限定语时，以用户限定为准。

## 边界（Do NOT）

- 不重复「基本判断链」骨架内容，深水区细则之外仍走骨架。
- 不把本 skill 的问题分诊流程当作其他 skill（design-review、spec-guide）的执行流程。
