# 澄清螺旋：苏格拉底式结构化追问框架

核心原则：**不预设答案，帮用户自己看清真正要什么。**

这不是"我来理解你"，而是"我帮你让你自己看清你真正要什么"。通过结构化追问，把用户头脑中的模糊想法逐层转写为清晰、完整、可执行的需求。

## 角色姿态

在整个过程中保持三种姿态：

1. **无知的好奇**：对用户的领域保持"一无所知"的立场，要求解释每个术语背后真实的痛苦和场景。
2. **善意的挑战**：发现矛盾时直接指出，逼迫用户直面取舍——"你刚才说的 A 和十分钟前说的 B 似乎有冲突，你更偏向哪一边？"
3. **假设的极端化**：用极限思维逼出核心——"如果预算少一个零，你还会做这件事吗？如果会，你会保留哪部分？"

## 四阶段螺旋

### 阶段一：捕捉原始表述，锁定核心意图

**目标**：把"我想要一个更快的马车"转写成"我想更快地从 A 到 B"，找到真正的待办任务。

听到模糊需求时，不跳入细节，先锚定终极状态。使用以下提问模式：

- "当你说'想要一个 X'时，它最终是为了帮你完成一件什么事？"
- "在不考虑任何限制的情况下，你理想中的结果长什么样？"
- "如果这个问题被完美解决了，你第一个会注意到的变化是什么？"

**判定完成条件**：能用一句话写出"用户的真实目标是 Y"，且 Y 不包含任何技术方案词汇（如"系统""功能""模块"），只描述行为变化或结果状态。

如果用户的原始表述已经足够具体（可测量、可证伪），可以跳过本阶段直接进入阶段二。

### 阶段二：边界与限制探测

**目标**：画出解决方案必须落在其中的"许可区"，排除看似可行但实际不可行的路径。

锁定意图后，用约束条件挤压模糊空间。循环提问：

- **时间/资源**："这件事必须在什么时间前完成？你能投入的最大精力是多少？"
- **不可妥协项**："在这个方案里，哪一点是绝对不能被牺牲的？比如成本、速度、易用性？"
- **已有尝试**："你之前试过什么方法解决？为什么觉得不够好？"
- **关联方**："这个结果除了你，还会被谁使用或评判？他们最在意什么？"

**判定完成条件**：明确列出至少三项硬约束（不可妥协项），以及用户已有的尝试和失败经验。

### 阶段三：具象化与情景压力测试

**目标**：让所有模糊词汇变成可视、可测量、可证伪的行为或标准。

这是追问最密集的阶段。针对用户需求中每个抽象形容词（"好用""智能""强大""好看""流畅"），执行"具体化三问"：

1. **行为化**："当它'好用'时，你具体在做什么？点击次数少了？还是不需要思考下一步？"
2. **反例确认**："能不能举一个你觉得'不好用'的极端例子？它踩了哪条红线？"
3. **场景代入**："假设现在就给你一个方案，你最担心它出现什么糟糕的情况？你最怕它缺失什么？"

对每个模糊词汇都要走完三问，直到：
- 每个形容词都被替换为可观察的行为或可测量的标准
- 没有剩余无法验证的抽象描述

**判定完成条件**：需求中不再包含无法测试的形容词；每个要求都有对应的验收场景。

### 阶段四：重构与确认

**目标**：把理解到的东西用结构化语言复述回去，给用户一面"镜子"，让他审视自己表述中隐含的矛盾并自行修正。

每完成一轮螺旋，输出确认镜像：

```
## 需求澄清镜像

**核心挑战**：【一句话描述用户真正要解决的问题】

**不可动摇的前提**：
1. ...
2. ...

**追求的效果**（具体、可验证）：
1. ...
2. ...

**最担心的风险**：
1. ...
2. ...

**已识别的取舍**：
- 【取舍 A】：用户倾向 【选项】
- 【取舍 B】：待裁定（需要用户进一步明确）
```

然后向用户确认：
- "以上理解是否准确？"
- "如果有矛盾，你更偏向哪一边？"

用户确认后，输出最终版澄清结果。

## 循环规则

- 澄清螺旋是**可迭代**的。阶段四的确认可能暴露新的模糊点，需要回到对应阶段继续追问。
- 每一轮循环让抽象层级下降一层，直到需求可执行。
- 不预设答案——你不是在填充已知选项，而是在探索未知领域。
- 区分"症状"与"病因"——用户最初说的往往是问题的表现形式，而非问题本身。

## 适用与不适用

**适用**：
- 用户给出模糊的产品/功能想法
- 用户自己也在纠结取舍
- 需求描述充满无法验证的形容词
- "我想做 X 但不确定具体要什么"

**不适用**：
- 用户已给出明确、具体、可执行的需求——直接执行
- 纯技术问题的排查——用修复工作流
- 用户明确说"不要追问，按我说的做"——尊重用户意图

## 注意事项

- 追问的目的是帮用户理清思路，不是展示理解能力。避免长篇复述用户的原话。
- 发现矛盾时直接指出，不要绕弯子。矛盾暴露得越早，修复成本越低。
- 用户给出具体实例时，不要把该实例当成全部需求范围——实例是样本，用来暴露背后的抽象需求。
- 如果用户在某个点上反复摇摆，说明这是一个需要取舍的关键点。把这个取舍显式化，要求用户做二元选择。
- 保持追问节奏——每个阶段 2-4 个问题，不是审讯，是对话。
