# Spec 大改/骨架级重构的破锚指引

本文件是 SKILL.md「Spec 生命周期管理」中大改破锚一条的展开。spec-guide 的场景 C 原本只覆盖"小改"，但判定为大改时存在一个结构性陷阱：**旧 spec 会在同线程中锚定主 Agent，使其产出保守微调而非实质重构**。本文件补齐这个场景的机理、触发条件、解构方法、集群纪律与证据基础。

适用范围：场景 C 变更评估判定为**大改**（定稿历史化）的 spec 重构。小改（澄清、补边界、修笔误）不需要破锚，走正常场景 C。

## 一、问题定义：什么是"旧 spec 锚定"

当任务是**改写现状 spec**（大改 / 骨架级重构，而非小修小补）时，主 Agent 倾向于把旧 spec 当作 **ground-truth 前提**，而非**待改写的对象**。结果：即使旧 spec 的某条声明本身就是重构目标，Agent 也会围绕它做贴合现状的保守调整，而不是实质性地推翻它。

这不是"Agent 不够大胆"或"prompt 写得不够好"——这是**结构性的上下文机制**，靠提示措辞无法可靠破除（见第三节机理）。

典型表现：
- 用户说"重构这个 spec"，Agent 产出的是"旧 spec 的微调版"而非"基于新目标的新 spec"。
- 旧 spec 的结构、分节、术语被原样继承，即使其中有些本应是重构对象。
- 对话越长、旧 spec 在上下文里出现得越完整，这种倾向越强。

## 二、为什么大改会触发这个陷阱，小改不会

小改（澄清、补边界、修笔误）时，旧 spec 确实是 ground truth——它不该被推翻，只该被补充。此时"以旧 spec 为前提"是**正确行为**。

大改（骨架级重构、主口径变更、不可逆决策翻转）时，旧 spec 中有一部分声明的地位必须**从"前提"降级为"待审材料"**——它们恰恰是重构的对象。如果 Agent 仍把它们当前提，重构就无法发生。

判定为大改的信号（见 `lifecycle.md`）：
- 同一节 3 次以上补丁式修订。
- 修订触及核心契约、状态所有权、主实体。
- 改完读者无法理解原初意图（原意图已被颠覆）。

## 三、机理：为什么必然发生（三层机制）

### 机制 1：锚定偏差（Anchoring Bias）

LLM 显著存在 anchoring bias——上下文中先出现的信息会锚定后续判断。关键证据：arXiv:2412.06593《Anchoring Bias in Large Language Models》证实，**Chain-of-Thought、Reflection、"忽略锚点"提示等简单提示技巧不足以消除锚定偏差**。注意是"不足以消除"：部分研究（如 Nguyen et al. 2024）显示 CoT 等技巧对某些变量有一定缓解作用，但不能稳定、彻底地破除锚定。

含义：**不可能靠"在主线程里换 prompt 措辞"（哪怕加 CoT、反思、"请大胆重写"）来可靠破锚**。这是必须用子代理隔离的结构性原因。

### 机制 2：检索即权威（Context Poisoning / Retrieval as Authority）

旧 spec 以"上下文内容"形式出现时，会被模型当作**权威输入**而非**待审材料**。安全侧研究把这类现象称为 context poisoning："一旦信息进入 agent 的活跃上下文窗口，它就会被反复复用"。在非恶意场景下，这套机制表现为：检索到的现状内容被当作已验证事实，而非待质疑的假设。

### 机制 3：指令层级冲突（Instruction Hierarchy）

旧 spec 作为"上下文内容"与"请重构它"的指令同线程出现时，OpenAI 指令层级理论预测：模型倾向于把"上下文内容"当作**低优先级的指令式约束**去服从，而不是当作**指令所指的操作对象**去改写。于是"重构 spec"的指令被弱化，"保持 spec 大体不变"成为隐含默认。

## 四、核心方法：解构，而非重写

破锚的本质**不是让 Agent"更大胆"**——研究已证明提示层面的"大胆"指令不可靠。破锚的本质是**改变旧 spec 信息进入新 spec 编写过程的地位**：从"约束"降级为"待审材料"。

具体手段：调用「破锚解构师」subagent，对旧 spec 逐条声明做**四分类解构**：

| 分类 | 含义 | 处置 |
|------|------|------|
| **真约束（keep）** | 追溯到业务规则/外部契约/不变量。删掉它，系统正确性会破坏。 | 原样带入新 spec |
| **锚（watch）** | 看起来像约束，实为过去某个实现决策的遗留。存在是因为"一直这样"，不是业务要求。⚠️ 最危险——主 Agent 最容易把它当 ground truth。 | 显式标记，从约束降级为"待审假设"，新 spec 可推翻 |
| **待改写（target）** | 这条声明本身就是重构要改变的对象。 | 显式标记为 target，新 spec 必须给出替代口径 |
| **待删除（obsolete）** | 已被取代/从未生效/死口径。 | 不带入新 spec，走 lifecycle.md 退役流程 |

解构完成后，**主线程拿到的输入是解构报告**（真约束已被提取、锚已被中和、目标已被显式标记），而不是旧 spec 原文。主线程以此为基础走场景 A 编写新 spec。

关键纪律：解构发生在**子代理的独立上下文**里，旧 spec 的全文留在子代理内部，只回传浓缩的解构报告——这从物理上切断了"旧 spec 全文污染主线程"的通道（机理见 Anthropic context engineering，第六节）。

## 五、工作流集成：如何嵌入 spec-guide 的 A/B/C 流程

```
场景 C 变更评估
  ├─ 判定为小改 → 走正常场景 C（旧 spec 是 ground truth，正确行为）
  └─ 判定为大改（定稿历史化信号命中）
       │
       ▼
  ⚡ 破锚解构（委派破锚解构子代理，能力引用见「九、与相关子代理的边界」）
       │  输入：重构目标(Why) + 旧 spec（作为待审材料，非前提）
       │  输出：四分类解构报告 + 2-3 个独立重构方向入口
       │
       ▼
  场景 A 编写新 spec
       │  输入：解构报告 + 重构目标（❌ 不是旧 spec 全文）
       │  主线程上下文只持有解构后的约束与目标，不持有旧 spec 原文
       │
       ▼
  旧 spec 标 Superseded（走 lifecycle.md 定稿历史化流程）
       │  新 spec 首部写「与前任 spec 的关键差异」
       │  引用清理 → 旧 spec 转 Archived
```

**为什么解构必须发生在子代理而非主线程**：若在主线程内解构，旧 spec 全文已进入主线程上下文，锚定已经发生——解构报告本身会被旧 spec 的措辞权威感污染。子代理的独立上下文是破锚的物理前提。

## 六、集群用法（多实例编排与交叉验证）

当重构规模大、或需要对解构结论做交叉验证时，主 Agent 可并行调用多个破锚解构师实例。但多代理编排有结构性陷阱，必须遵守以下纪律。

### 陷阱：naive 多代理辩论会"信念固化"

arXiv:2503.16814《From Belief Entrenchment to Robust Reasoning in LLM Agents》发现：naive 多代理辩论（MAD）**不会纠错，而是放大初始多数意见**——无论该多数意见对错。其概率模型与实验数据拟合良好（残差约 -2.5%）。

**关键限定（必须理解）**：MAD 是"多数放大镜"。当初始多数/共享先验**正确**时，辩论会巩固正确答案（这正是 Du et al. 2023 报告 MAD 正面效果的来源）；当初始多数/共享先验**错误**时，辩论会固化错误。

对本场景的含义：**如果所有破锚解构师实例都读了同一份旧 spec、用同一视角，它们的先验就被旧 spec 同一锚定，多实例"交叉验证"只会变成旧 spec 的集体证成**——比单实例更隐蔽、更危险。

### 纪律 1：每个实例必须拿独立的视角提示

多实例的价值在于视角多样性，不在于数量。给每个实例不同的解构视角，例如：
- 实例 A：**契约一致性视角**——只问"这条声明是否对应真实的外部契约/不变量"。
- 实例 B：**领域建模视角**——只问"这条声明是否反映领域本质，还是某个实现的投影"。
- 实例 C：**演进历史视角**——只问"这条声明是初始设计就有，还是补丁累积出来的"。

同一视角跑多份是伪多样性，是回声室（echo chamber）。

### 纪律 2：收敛判据是"异议有据化解"，不是"多数一致"

多实例产出后，收敛信号是：**所有分歧点要么被证据化解，要么显式停靠给人工裁决**。绝不能用"多数实例一致"作为收敛判据——那恰恰是信念固化的陷阱。多数实例同时被同一锚定，它们的"一致"没有意义。

### 纪律 3：独立生成在先，交叉暴露在后

先让各实例**各自独立产出解构报告**（互不可见），再进入交叉暴露阶段（各实例看到其他实例的结论，对异议作出回应）。不要让实例从一开始就共享同一份解构草稿——共享草稿会引入共享锚定。

### 推荐编排

- **规模**：2-3 个实例，各自独立视角。
- **轮次**：1 轮独立生成 +（可选）1 轮交叉暴露。
- **收敛**：人工（主 Agent 或用户）汇总异议，逐条判"已化解 / 停靠人工"。

## 七、证据基础

本指引的核心方法均有研究或官方工程依据。以下按强度排列，并标注书写限定条件（诚实呈现证据边界）。

| 论断 | 来源 | 强度 | 书写限定 |
|------|------|------|----------|
| context rot（上下文越多回忆越差）、attention budget、subagent 独立上下文、只回传 1-2k token 摘要、separation of concerns | [Anthropic 官方工程博客](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)；[Claude Code subagents 文档](https://code.claude.com/docs/en/sub-agents) | **最高（一手官方）** | 逐字命中，可放心引用 |
| LLM 锚定偏差存在；CoT/反思/"忽略锚点"提示**不足以消除**锚定 | [arXiv:2412.06593](https://arxiv.org/abs/2412.06593) Lou et al.（含期刊版 JCSS 2026） | 高 | 写"不足以消除"，不写"完全无效"（反方证据显示部分技巧对部分变量有缓解） |
| naive 多代理辩论会信念固化，放大初始多数/共享先验 | [arXiv:2503.16814](https://arxiv.org/abs/2503.16814) Oh et al. | 高（需限定语） | 必须写清"MAD 是多数放大镜；先验正确时巩固正确，先验错误时固化错误"——否则会与 Du et al. 2023 的正结果自相矛盾 |
| AI coding agent 重构时倾向 localized & conservative，高层接口级改动占比低于人类，设计 smell 改善 Δ≈0 | [arXiv:2511.04824](https://arxiv.org/abs/2511.04824) Horikawa et al. | 中高 | ⚠️ **标注"arXiv 预印本（2025-11），尚未见正式发表记录"**；Δ≈0 特指 design smell，非结构性指标 |

补充证据：
- Du et al. 2023 [arXiv:2305.14325](https://arxiv.org/abs/2305.14325)：多代理辩论的正面效果来源——作为 2503.16814 的对称面，说明 MAD 在先验正确时有效。
- Smit et al. ICML 2024：在合理预算下 MAD 不稳定优于 self-consistency——支持"多候选对照 ≥ 合并叙事"。
- LangChain 工程指南：多代理系统应 spawn fresh subagents with clean contexts。

## 八、反模式清单

1. **在装满旧 spec 的主线程里直接发"重构这个 spec"**——锚定 + 指令层级冲突双重作用，产出保守微调。（arXiv:2511.04824 实证统计的默认行为）
2. **只靠 prompt 破锚**（加 CoT、反思、"请大胆重写"）——arXiv:2412.06593 明确这些"不足以消除"锚定。
3. **让所有破锚/批判子代理共读同一份旧 spec**——信念固化：批判退化为旧 spec 的集体证成。（arXiv:2503.16814）
4. **用"多数一致"作为多实例收敛判据**——多数实例可能被同一锚定，"一致"无意义；正确判据是"异议有据化解"。
5. **只调用一个破锚实例，无任何对照**——单实例无参照系，无法发现被错杀的真约束或漏标的锚。
6. **用"旧测试全绿"作为重构唯一验收**——当目标是改变行为/架构时，旧测试全绿反而证明什么都没改。验收应来自重构目标的显式断言，而非旧行为的保持。

## 九、能力引用与降级路径（通用层与客户端分层）

破锚解构与架构设计是**能力**，不是绑定的具体实例（通用层与客户端分层规则见 AGENTS.md）。引用方式：能力名 + 当前环境的已知注册名 + 降级路径。

| 能力 | 层次 | 性质 | 职责 |
|------|------|------|------|
| **破锚解构** | Spec 声明层 | 诊断性 | 解构旧 spec 的锚定力量，四分类 + 重构方向入口。不建设。 |
| **架构设计** | 代码/架构层 | 建设性 | 从零出理想架构 + 诊断架构偏差 + 演进路线。建设完整方案。 |

两者互补：破锚解构诊断"旧 spec 哪里是锚"，架构设计建设"新架构应该是什么"。在一次完整的大改重构中，典型顺序是先解构（产出约束清单 + 中和锚），再基于解构报告（而非旧 spec）做理想架构设计。

**当前环境的已知注册名**：ZCode 注册表中破锚解构对应 `pomaojiegoushi` 子代理；架构设计对应 `jiagoushi` 子代理（⚠️ 当前环境未必注册，消费前以实际注册表为准）。

**降级路径**（无注册子代理的环境，或注册名不可用时）：委派一个全新 `general-purpose` 子代理，把本文件的**四分类契约**（真约束 / 锚 / 待改写 / 待删除 + 2-3 个独立重构方向入口）完整写进委派契约执行。关键约束是**独立上下文**（旧 spec 全文留在子代理内部，只回传解构报告），不是具体实例——只要做到物理隔离，任何等价子代理都能承担破锚解构。
