# 实现与重构纪律（implementation-discipline）

## 职责归属

- 新增逻辑先判断职责归属：越过当前模块/文件职责时，先放到正确的位置（新模块、新层、新接口、新组合关系）再补业务逻辑；只有职责完全一致且不制造边界混乱时，才允许在原文件扩写。禁止因为文件离入口近、下手方便，就持续堆不同职责。

## 主抽象复用

- 新增类型、组件、模块、接口、契约、服务、工具链前，必须确认是否已有可承载的主抽象；存在性确认不能只搜一个关键词，须用主名、别名、业务词、技术词、导出名、文件名、测试名等多组线索。
- 已有抽象能承载时优先复用、扩展或修正；方向正确但能力不足时补齐主抽象，禁止绕开新建局部实现；确需新增时，必须说清与既有抽象的职责差异、边界关系和不可合并原因。

## 唯一版本

- 发现重复实现、命名不统一、概念重复、入口重复时，必须定下唯一版本，删除、迁移或降级非唯一实现。禁止把"两个东西对不上号"降级为代码风格问题；它是架构分叉风险。

## 门禁裁定

- 触发行数、复杂度或格式门禁时，必须回到职责拆分、模块边界或门禁规则是否合理来裁定；禁止用压缩行、破坏缩进、合并无关语句、三元链替代 if/else 等牺牲可读性的写法规避门禁。行数超限是职责膨胀的信号，不是格式问题。

## 兼容与清理

- 快速开发与重构期不默认维护历史兼容；已确认、根因明确、影响当前主链的问题默认本轮处理干净。禁止用"后续优化""以后统一重构""暂时兼容""先保留两套"掩盖职责混乱或双线设计。
- 被取代或不再适用的产物（设计稿、spec、原型、计划文档、代码、测试）当轮删除，并同步清理其引用（配置、入口注册、文档交叉引用、导航 map），历史留存交给版本库，不靠工作区文件堆积。
- 清理标注「过渡期保留」「阶段N 将删除」「@deprecated」的产物前，必须先证伪它声明的存活理由：① 对可疑消费方查真实调用方（引用它的那个客户端本身可能也是死代码）；② 确认它对外的端点、入口或装配点是否真的存在（可能从来不存在、只是没人发现）；③ 找出唯一真实依赖，把它降级到最近的合法 owner（就近自带常量 / 类型），再整文件删除。三步做完只剩弱依赖时做整文件替换，不做部分保留——部分保留等于留下第二套事实源。理由：「待删」标记写下的时刻成立，之后消费方死掉或端点消失，标记不会跟着更新，按标记决定删除粒度必然留下固化的错误依赖。
- 修复需要添加兼容分支、临时适配或旁路 helper 才能通过时，必须先想清楚是否存在职责边界、契约语义或主抽象问题。

## 架构论证

- 架构建议不得拿代码库现有实现当依据——现有实现只能证明现状，不能证明方向对；架构目标是按业务走通闭环，明确职责、边界、契约、约束与唯一定义。确认骨架无误后，应降级为实现修复、测试修正或环境处理，架构分析不得无限扩大问题。

## 测试

- 测试保护当前业务闭环和契约语义，而不是固化旧说法。用户新需求优先于已有测试；测试失败时先按 problem-triage 定性根因，再裁定测试保护的是新需求、旧行为还是无效假设——保护旧行为的测试应删除或改写，禁止过时测试反向决定新需求的实现方向。

## 无测试设施时的渲染验证

项目没有测试框架时，不要为「验证一次」引入测试设施；用服务端渲染 / DOM 解析拿可逐条比对的确定性输出，不要只靠截图。临时 entry 验证完即删，不留 `src/`。适合断言结构与文案、破损输入不抛异常；版式与观感不归 agent 判，按 visual-handoff 交用户。

具体命令（以 React/TSX 为例）、`--format=cjs` 的原因与断言边界见 `references/verification-recipes.md` 第 1 节。

## 设计层提交基准

- 本轮产生了设计层决策性变更（spec、设计文档、原型、AGENTS.md 等设计层产物中的契约、职责、边界、状态所有权变化），且设计已拍板、即将进入实现层时，若本轮开工时工作区是干净的，主动提议将设计层变更单独提交（附建议的提交信息），用户确认后执行。理由：先把设计定成基准，后续实现的 diff 才能暴露实现过程中对设计层的无意偏离。
- 纯措辞/格式修正不触发；开工时工作区不干净不触发（有存量改动时避免卷入，改为提示用户自行处理）。

## 依赖包安装验证

- 安装依赖包时，禁止依赖自身知识库或记忆判断包名、版本号或安装方式，这些信息可能过时。必须通过在线验证（官方仓库、包管理器 registry、官方文档）确认正确的包名和可用的最新稳定版本，优先安装最新稳定版。

## 验证命令一次拿全结果

跑门禁、构建、测试等验证类命令时，单条命令内必须同时完成输出落盘与退出码捕获：

```bash
pnpm check:xxx > /tmp/gate.log 2>&1; echo "exit=$?"; tail -20 /tmp/gate.log
```

- 禁止用 `| tail` / `| grep` 直接接验证命令——管道会吞掉被验命令的退出码，导致为拿结果多次重跑长耗时门禁。
- 汇报验证结论必须以退出码 + 落盘日志为准，不得以"没看到报错"推断通过。

### 长链路分段计时

怀疑某条多段链路整体慢时，先用分段计时量出每段耗时，再定位优化点；优化前后用同一段清单对比。脚本用法、库模式与日志格式见 `references/verification-recipes.md` 第 2 节。

## 门禁报红的归属判定（先基线，后动手）

门禁/回归/校验报红时，先分清「本轮改动引入的」还是「改动前就存在的」，再决定是否动代码。基线对比的具体命令（git archive 只读导出 + 复用依赖）见 `references/verification-recipes.md` 第 3 节。

- 两边失败行与数字逐位相同即判定存量红，与当轮改动无关——比 `git stash`（要写工作区、有丢改动风险）和「读代码推断没影响」（无证据）都可靠；副本在 /tmp，跑完即弃。
- 上报前先把失败信息做成可直接行动的形态：点名对象业务名 + 类型 id、实配值 vs 下限、差值来自哪个分量、数值出处；数值取舍归用户（自己去编辑器调），不代改数值、不主动提议放宽或删除校验。理由：判据不透明的红项会把分析成本全推给用户，而「改口径」最容易被误当成收口方式。
- 归属未判定前不要动代码「修红」——把存量红当成本轮引入，最容易改坏与本次任务无关的数值或校验。

## 状态变更命令（终止/删除）执行纪律

- 终止进程、删除文件等状态变更命令：报错不得重定向吞掉，成败以复核结果为准——目标确实消失、指标确实回落；不能凭单一快照字段下结论。理由：吞错 + 无复核曾造成对用户误报「已清理成功」。
- 沙箱化 shell 拒绝信号类操作时，显式提权重试，不换花样绕过；清理失控进程属正当场景。
- 进程甄别先看进程名特征与 PPID，不按 runtime 名一刀切；macOS 的具体判据（`PPID==1`、RSS/swap 假象）见 `references/verification-recipes.md` 第 4 节。

## 边界（Do NOT）

- 不重复「基本判断链」骨架（层级路由/定性/归属/裁定/收尾）；那在 AGENTS.md 常驻。
- 异常与报错的根因定性、测试失败的原因归属、重构信号判断不归本 skill，走 problem-triage。
- 任务收尾的残留清理不归本 skill，走 sweep。
