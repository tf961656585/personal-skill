# 决策提问：让用户看得懂、能拍板的写作规范

## 为什么需要这个 schema

Agent 提问前通常刚做完大量探索：读过代码、比过 spec、理清了调用链。用户没有经历这个过程。当 agent 把脑内高度压缩的结论直接抛成问题，用户看到的就是一串没有前因后果的黑话——不是用户水平不够，是信息不对称没有被抹平。

提问的唯一目的是让用户**拍板**。拍板需要的不是"问题本身"，而是"足够做判断的上下文"。所以每个裁决点提交前，必须把 agent 在探索中获得的、与这个决策相关的上下文，用业务语言还原给用户。

## 判定：这个问题该不该问

写之前先过一遍「提问与用户裁决」规则（user 级）：要事实走代码自查，不问用户；要取舍（意图、方向、范围、定义）才问。schema 只服务于后一类。

## 决策简报 schema

每个裁决点按以下六段写。顺序即逻辑链：先知道"在说什么"，再知道"现在怎样"，然后"哪里卡住了"，最后"请你做什么"。

### 1. 请你定什么

一句话说清裁决点，用行为/意图语言，不含仓库内部标识符。

- 好：「定时任务挂了之后，是自动重试还是等人来处理？」
- 坏：「`RetryPolicy` 用哪种策略？」

### 2. 这是什么

用业务语言交代涉及的机制或对象。仓库内部概念首次出现时，先给业务解释再标注对应物：「负责订单超时关闭的定时器（`OrderCloser`）」。

判定标准：一个没读过这个仓库、但懂业务的同事，读完这段能知道你们在谈什么东西。

### 3. 现状与发现

交代自己探索到的事实，并注明证据来源：

- 代码里现在是怎么做的（已核实）→ 「代码里现在……」
- spec 里设计但实现状态未核实 → 「按 spec 设计是……，实现状态未核实」
- 多处说法并存、没有唯一定义 → 如实说分裂，不挑一个当事实

不假定用户记得前序会话的调查结论——哪怕上一轮刚查过，关键事实也要重新交代（一句话即可）。

### 4. 为什么需要你拍板

说清缺口或矛盾是什么，以及为什么 agent 不能自己定。这条是诚意所在：让用户明白这个问题不是 agent 偷懒甩锅，而是真的卡在意图/方向/范围上。

- 好：「两种实现都能跑，但一个保最新数据、一个保不丢历史，保哪个取决于这个列表的用途是监控还是审计——这是用途定义问题，得你定。」
- 坏：（不写，直接抛选项）

### 5. 可选项

2-4 个真实可选方案，每个装**行为/意图/取舍**，附一句代价或后果。代码对应物只作证据标注，不当选项本体。不用"好/中/差"式选项衬托推荐项。

- 好：「订单超时 30 分钟自动关闭（实现简单，但用户支付慢时会误关）」
- 坏：「方案 A：30 分钟超时；方案 B：更好的方案」

### 6. 我的倾向

作为资深伙伴给出自己的倾向和一句理由。拍板权在用户，但"没倾向"会把分析成本转嫁给用户。没有倾向时如实说明卡在哪个未知事实上。

## 语言规则（针对"黑话"根因）

- **首次出现即翻译**：每个仓库内部名词、缩写、机制名，第一次出现时配业务语言解释。解释里又引入新术语时继续展开，直到落到用户已知概念。
- **内部黑话不外说**：spec/skill/AGENTS.md 里的专门词（如"收口""主抽象""冒烟"）是内部工作语言，对用户说"定下来""唯一的正主实现""最小可用性验证"。
- **一个问题自包含**：用户可能只看其中一个裁决点。每个问题独立可读，不靠"如上所述""同上"指代。
- **数字和事实具体化**：「最近经常失败」→「过去 7 天失败 12 次」。

## 载体映射

### 结构化选项提问（首选）

工具字段短，塞不下上下文链。采用**工具前铺垫 + 工具内精简**：

1. 先用自然语言输出完整决策简报（六段），每个裁决点一节。
2. 再调用结构化选项提问能力（当前环境注册名：`ask_user_question`；其他环境可能是 `AskUserQuestion`）：
   - `question`：第 1 段的一句话裁决点（可读，不含标识符）
   - `header`：≤12 字的短标签，起索引作用
   - 选项 `label`：行为/意图短语
   - 选项 `description`：该选项的代价/后果一句话
3. 推荐项按工具惯例放第一位并标注。

### 纯文本 / 规划模式待决策清单

完整输出六段决策简报。多个裁决点各自成节，编号清晰。

### 汇报中夹带的待确认项

探索汇报、交付汇报里夹带"需要你确认"的事项时，同样过 schema，不因为是"顺便一提"就省略上下文链。

## 自检清单（发出前逐条过）

- [ ] 删掉所有仓库标识符后，用户还能读懂问题吗？
- [ ] 每个术语首次出现时都配了业务解释吗？
- [ ] 现状/发现注明了证据来源（代码已核实 / spec 设计未核实 / 分裂）吗？
- [ ] 说了"为什么需要你拍板"吗？
- [ ] 每个选项都带代价/后果，且没有"好中差"陪衬吗？
- [ ] 给了自己的倾向（或如实说明卡在哪）吗？
- [ ] 单个问题脱离其他问题也能读懂吗？

## 反例与正例

**场景**：agent 探索游戏仓库后发现有两套敌人生成逻辑，需要用户裁决保留哪套。

❌ 反例（三个根因全踩）：

> 发现 `EnemySpawner` 和 `SpawnDirector` 职责重叠，建议收口到主抽象，你倾向保留哪个？A. EnemySpawner B. SpawnDirector

问题：`EnemySpawner`/`SpawnDirector` 无解释（黑话）；"职责重叠""收口""主抽象"是内部语言；没说两套各是什么、为什么重叠、保留哪套有什么影响（无上下文链）。

✅ 正例：

> **请你定什么**：敌人生成逻辑保留哪一套，另一套删掉。
>
> **这是什么**：游戏里"敌人什么时候、在哪刷新"的逻辑。仓库里现在有两套代码在做这件事：一套是按关卡进度表刷怪的（`SpawnDirector`），一套是监听玩家位置动态刷怪的（`EnemySpawner`）。
>
> **现状与发现**：代码里两套都在运行（已核实），同一波怪可能各刷一遍导致数量翻倍；spec 里没有声明哪套是唯一实现（设计层未拍板）。
>
> **为什么需要你拍板**：两套对应两种不同的玩法手感——按表刷怪节奏可控，动态刷怪更紧张。保留哪套取决于你想要哪种体验，这是方向问题，我定不了。
>
> **可选项**：
> - A. 保留按表刷怪：节奏可控、好调试，但关卡变化少
> - B. 保留动态刷怪：体验紧张、复玩性高，但难度曲线难调
>
> **我的倾向**：倾向 A——当前只有 3 个关卡，动态刷怪的复玩性优势用不上，调试成本却实打实。

随后调用结构化选项提问能力，question 写「敌人生成逻辑保留哪一套？」，选项 label 写「保留按表刷怪」「保留动态刷怪」。
