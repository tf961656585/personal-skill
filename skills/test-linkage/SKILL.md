# 测试↔spec 关联与测试活性治理

本 skill 是测试侧关联与活性治理的单一工作流：建立关联体系、执行变更点名、跑全仓审计、处置存量漂移。

## 问题定位

spec 侧有成熟的收敛机制（生命周期状态机 + 变更记录表 + 退役登记），测试侧没有任何对应的收敛动作。能力退役、语义翻转、重新设计之后，spec 里口径清零，测试里静默滞留——旧行为测试继续绿着，无人发现。已实证的失效形态：

| 失效形态 | 实例特征 | 机制覆盖 |
|---|---|---|
| 旧行为固化 | 测试绿，但断言保护的是 spec 已废弃/已翻转的语义 | **强覆盖**（R1 生命周期闭包 + R3 点名） |
| 无关联测试 | 大量测试无任何 spec 锚点，无法判断保护对象是否现役 | 直接覆盖（R6 可见性 + 增量收敛） |
| 孤儿测试文件 | 不被任何运行入口的 glob 覆盖，从不执行 | R4 |
| 沉睡测试 | skip/todo 或断言旧口径，跑了也不设防 | R5 清单 + 人工裁定 |
| 词汇/夹具滞留 | 测现役行为但用已退役词汇命名/造夹具 | R1 点名时顺带暴露 |
| 保真度缺陷 | 语义对但链路被桩架空，各层全绿主链断 | R10（接缝禁桩）+ 接缝测试范式 |

机制解决「发现与点名」：把语义判断的对象集从全量测试缩小到变更波及的一小批；「确认是否仍保护现役语义」的最后一步是人工裁定。

## 核心原则

1. **事实源只有两处，且都就近**：验收 ID 定义在 spec 正文，标注写在测试文件。**禁止**引入第三处集中映射文件（登记物与被登记物物理分离必然漂移——集中登记表的守卫字面量双写、导航 pointers 均有漂移实证）。一致性由双向校验保证。
2. **挂接跃迁点，不挂接日常**：只在 spec 生命周期跃迁（status 迁终态、验收项标废弃）与语义变更时强制发力，日常只做 advisory 可见性。
3. **选择性绑定**：只有 spec 驱动的行为测试要求绑定；纯实现细节测试、工具/守卫自测、fixture 校验合法地不绑。覆盖率是代理读数（见 spec-guide consistency-checks.md §七），不设阈值、不进状态机。
4. **就近标注抗漂移**：标注随测试文件同生命周期——文件删除标注即消失，天然同步；错误标注由引用闭包校验兜底。
5. **红过真问题再升硬**：新规则先 advisory 输出清单，红出一次真问题、存量清完后升硬门禁。避免校验器变成无人理会的警报器。

## 体系分层

| 层 | 内容 | 事实源 |
|---|---|---|
| 1. ID 契约 | spec 用 `#### 验收：<ID>` 承载可测试行为点；ID 全局唯一、随 spec 生命周期；显式废弃用 `#### 废弃：<ID>`（ID 保留原文、语义不再验收） | spec 正文 |
| 2. 测试标注 | `// @spec: <ID>[, <ID>]` 独占一行注释；文件头（粗粒度）或用例上方（细粒度）均可 | 测试文件 |
| 3. 一致性校验器 | R1/R2/R4/R5/R6/R10 规则扫描，error 阻断 / warning 输出 | `scripts/check_test_linkage.py` 或仓库自持守卫 |
| 4. 变更流程钩子 | spec 变更记录波及验收 ID 时输出受波及测试清单，退役批次逐项处置 | 流程纪律（见 linkage-spec §5） |
| 5. 审计报告 | 覆盖读数与漂移趋势，只看不罚 | 校验器输出 |

规则明细（判据、分档、豁免机制、裁定动作）见 `references/linkage-spec.md`。

## 与 spec-guide 的分工（不重复建体系）

- **格式约定同源**：ID 格式（`<域缩写>-<序号>`）、标注 schema（`@spec:`）、编号稳定性（禁复用旧号）、书写陷阱，全部以 spec-guide `references/consistency-checks.md` 为唯一规范源。本 skill 不重复定义，只消费。
- **spec-guide `trace_acceptance.py`**：单 spec 视角，服务「实现完成后回验」与「场景 C 变更后核对」，含「缺失测试」阻断（spec 有验收项、测试无标注）。
- **本 skill 校验器**：全仓视角，服务门禁与定期审计，含 spec-guide 工具做不了的部分：跨 spec ID 唯一性（R2）、生命周期闭包（R1——标注 ID 必须属于 **Active** spec，终态 spec 的 ID 下架即红灯）、测试活性（R4/R5）、接缝禁桩（R10）。**不做**「缺失测试」阻断（33 个存量验收 ID 无标注是常态，强制会把门禁变红海；该判定留在 spec-guide 回验场景）。

## 工作流

### 场景 A：建立/接线关联体系

1. 确认 spec 侧验收 ID 惯例已立（无则按 spec-guide 场景 A 的「验收项创建即配 ID」纪律补）。
2. 在测试侧推广 `@spec:` 标注 schema，从已有验收小节的 spec 对应测试开始。
3. 选校验器载体：通用参考实现 `scripts/check_test_linkage.py`（配置驱动，任何项目可用），或按项目门禁惯例自持守卫（如 Node 项目在 `tooling/scripts/` 写 mjs 守卫，规则语义以 linkage-spec 为准对齐）。
4. 第一跑必然出存量红灯清单——**这就是基线报告**，逐项裁定后清零，再决定各规则的分档（先 advisory，红过真问题升硬）。
5. 把守卫接进项目门禁链（静态扫描类接类型检查/lint 同级），并把标注 schema、规则分档、入口 glob 同步纪律写进项目的门禁口径文档。

### 场景 B：spec 变更/退役批次的点名与处置

1. spec 侧完成变更（语义改写 / 验收项废弃 / status 迁终态），变更记录表落行，`影响范围`列写明波及的验收 ID。
2. 跑校验器：R1 红灯清单即「受波及测试清单」（废弃 ID 与终态 ID 的全部引用者自动点名，无需人工 grep）。
3. 逐项裁定（三选一，参照 spec-guide consistency-checks.md §五）：**删除测试**（行为整体退役）/ **改测新口径**（语义翻转，断言改写+改标注到新 ID）/ **显式豁免**（legacy 保留须附原因）。
4. 处置完成、校验器转绿后，变更批次才算收尾。禁止「退役了再说」。
5. 变更记录表的影响范围列同步写明关联测试处置方式（如「AG-CT-004 用例按 AG-CT-010/011 改写」）。

### 场景 C：全仓审计与报告解读

```bash
python3 scripts/check_test_linkage.py --root <仓库根> [--config <config.json>] [--format json]
```

- error 级（R1/R2/升硬后的 R10）：阻断，必须处置。
- warning 级（R4/R5/R6/未升硬的 R10）：输出清单，按趋势人工巡检；孤儿测试文件优先看（从不执行的测试是最彻底的过时）。
- 报告解读纪律同 spec-guide：覆盖率是代理读数不是状态机，未覆盖 ≠ 未实现。

## 失效案例沉淀协议

审计点名的每个存量漂移，处置时记录三件事：失效形态（对照上表）、滞留时长线索（spec 侧废弃日期 vs 测试残留）、根因（缺机制还是缺纪律）。这是判断「规则要不要升硬」的证据基础。
