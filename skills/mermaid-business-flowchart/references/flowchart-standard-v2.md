# Mermaid 业务流程图标准（V2）

## 1. 适用范围

- 本标准仅适用于 Mermaid `flowchart`/`graph` 语法。
- 用于业务专家与技术团队进行流程对齐、评审与交付。

## 2. 目标

- 让流程图既可被业务理解，也可被技术实现。
- 降低“口头需求 -> 实现偏差”的风险。
- 为后续代码实现提供可追溯的流程协议。

## 3. 强制规则（Must）

1. 唯一主流向  
流程必须保持单一主流向（推荐 `TD` 或 `LR`），减少回跳与交叉线。

2. 角色边界可见  
使用 `subgraph` 明确角色边界（用户、前端、后端、第三方、人工审核等）。

3. 决策节点可判定  
所有决策节点必须是 `{}`，且每条出口必须有标签（如 `是/否`、`成功/失败`）。

4. 异常路径显式化  
至少覆盖：校验失败、超时/取消、外部依赖失败三类异常中的相关项。

5. 终态可达  
至少一个成功终态与一个失败/关闭终态，所有主要路径都能收敛到终态。

6. 文案语义化  
节点文本采用“动词 + 名词”结构，避免技术实现细节（如 SQL、Redis 命令）。

7. 高风险标点必须加引号  
节点标签若包含 `: () [] {} |`，必须用双引号包裹，例如 `A["调用 reactflow:onNodesChange(dimensions)"]`，避免 Mermaid 解析歧义。

8. Mermaid-only  
不混用 BPMN/UML 符号语义；必要说明放注释，不切换图语言。

## 4. 推荐规则（Should）

- 外部调用节点补充 `超时/重试/幂等` 策略说明。
- 关键状态写入动作显式节点化（例如：`更新订单状态`）。
- 人工审核流程补充超时升级或默认策略。
- 大流程拆分为主图 + 子流程，主图只保留关键路径。

## 5. 反模式（Don't）

- 一个节点描述多个动作（例如“校验+支付+落库”）。
- 决策节点只有单分支。
- 只画成功路径，不画失败路径。
- 回跳到起点形成隐式无限循环。
- 用内部术语替代业务语义（如“调用 Redis 获取缓存”）。

## 6. 评审清单

- [ ] 是否只有 Mermaid 流程图语法？
- [ ] 是否有明确角色边界？
- [ ] 每个决策节点是否有至少两个有标签分支？
- [ ] 是否覆盖关键异常路径？
- [ ] 关键状态写入动作是否可见？
- [ ] 是否存在成功与失败/关闭终态？
- [ ] 用户是否已明确确认流程版本？

## 7. 落盘约定

- 推荐路径：`docs/flowcharts/`
- 推荐文件名：`<业务域>-<流程名>-v<版本>.md`
- 文件必须包含：
  - 背景与目标（1-3 行）
  - Mermaid 图块
  - 评审结论与确认信息（日期、确认人）
