# Mermaid 业务流程图技能

## 目标

将业务逻辑表达为 Mermaid 流程图，作为业务与技术之间的中间协议；在用户明确确认后，将最终版流程图保存到仓库。

## 强制边界

- 仅使用 Mermaid（`flowchart`/`graph`）表达流程，不输出 BPMN/UML 语法。
- 不猜测业务规则。缺少关键上下文时，先提出 1-3 个高价值问题再画图。
- 每个判断节点必须有清晰分支标签（如 `是/否`、`成功/失败`）。
- 关键异常路径必须显式建模（如校验失败、超时、取消、回滚/补偿）。
- 节点文案若包含 `: () [] {} |` 任一字符，必须使用双引号包裹（如 `A["调用 reactflow:onNodesChange(dimensions)"]`）。
- 未收到用户明确保存确认前，不写入仓库文件。

## 工作流

### Step 1: 收敛输入

基于用户描述整理最小输入：
- 业务目标（要解决什么问题）
- 关键参与方（用户、前端、后端、第三方、人工审核等）
- 成功路径与至少一条失败路径
- 是否存在异步回调、重试、人工介入

若信息不足，先问 1-3 个问题，避免“边猜边画”。

### Step 2: 产出首版 Mermaid 图

遵循以下约束：
- 主流向保持单一（左到右或上到下）。
- 节点文案使用“动词 + 名词”，例如：`校验支付参数`、`下发会员权益`。
- 每个泳道对应一个角色边界（可用 `subgraph` 表达）。
- 决策节点用 `{}`，并写清分支标签。
- 至少一个成功终态与一个失败/关闭终态。

### Step 3: 执行结构自检

优先运行：

```bash
python3 .codex/skills/mermaid-business-flowchart/scripts/validate_mermaid_flow.py --input <流程图文件>
```

该校验器会拦截高风险标签写法（例如未加引号的 `reactflow:onNodesChange(dimensions)`）。
校验通过后再进入评审；若失败，先修图再沟通。

### Step 4: 业务评审迭代

评审时固定检查：
- 角色边界是否准确。
- 决策分支是否互斥且清晰。
- 异常路径是否完备。
- 外部调用是否体现等待/回调/重试策略。
- 关键状态写入是否有明确位置。

必要时给出 v2/v3 图，直到用户明确“确认通过”。

### Step 5: 确认后落盘

只有用户明确确认后，才保存文件。确认语义示例：
- `确认保存`
- `可以落盘`
- `按这个版本写入仓库`

保存建议：
- 目录优先：`docs/flowcharts/`
- 文件命名：`<业务域>-<流程名>-v<版本>.md`
- 文件内容使用 Markdown + Mermaid fenced block，便于 PR 审阅。
- 当 Mermaid 作为 spec 的组成部分（非独立流程文档，而是 spec 内嵌的流程/状态机/时序图）时，落盘随 spec 目录内嵌，不单独落 `docs/flowcharts/`，但仍必须过本校验器。spec 内嵌流程的定位与落盘约定详见 spec-guide。

## 输出模板

### 1) 沟通版输出

- `流程目标`：一句话
- `关键参与方`：逗号分隔
- `Mermaid 流程图`：代码块
- `待确认点`：最多 3 条

### 2) 落盘版输出

- `保存路径`：仓库绝对或相对路径
- `版本`：如 `v1`
- `变更摘要`：1-3 条
- `Mermaid 流程图`：与文件内容一致
