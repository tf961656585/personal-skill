# 设计层入口（design-guide）

design 层是 spec 的父集合：spec、ADR、契约文档、原型、流程图都是设计层载体，各有表达优势。本 skill 是设计层创建任务的唯一入口，只做三件事：**判可逆性、选载体、路由**。

本 skill 不定义任何载体的创建、更新、审查细节——那些由载体专门工作流唯一承载。理由：设计层纪律的单一真实性依赖于每个载体只有一套生命周期规则，入口层复述或另立规则必然漂移。

## 首条规则：载体已定，直接路由

若用户已明确指定载体（"写 spec"、"更新这份 spec"、"做个原型"、"画张流程图"），路由决策已由用户完成，直接跳到对应工作流，不重复判可逆性。禁止为流程而流程、强制两跳。

## 第一步：判可逆性

- **可逆决策**（UI、交互、交互流程、体验、模块内部结构）→ 原型路径。UI/交互类需求例外：走「UI/交互类需求的交付顺序」四段式（设计文档 → 原型 → 评审 → 代码），该专章优先于本条默认；若用户明确要求"先落地设计层 / 先出设计文档"，路由到落地设计文档形态（见第三步）。业务流程对齐走流程图载体，不按可逆性判。
- **不可逆决策**（架构骨架、核心契约、接口语义、跨边界数据模型、状态所有权）→ spec 系载体。
- 混合型需求按决策拆分，各部分分别路由——一个需求完全可以"骨架落 spec、交互落原型"。
- 可逆性拿不准时，这是取舍不是事实，上浮用户裁决。

## 第二步：选载体

| 载体 | 表达优势 | 适用面 | 专门工作流 |
|------|----------|--------|------------|
| 原型 | 界面、交互、流程可运行、可验收，优于一切文字描述 | 可逆行为 | 原型路径（见第三步） |
| 落地设计文档 | 可逆决策但用户要求先出文档时，设计先行、实现后置的中间态产物 | 可逆行为（先出文档） | 落地设计文档形态（见第三步） |
| ADR | 半页内收口单个决策 | 单个或少数不可逆决策 | spec-guide |
| 契约文档 | 机器可校验（OpenAPI / AsyncAPI / JSON Schema） | 跨边界接口 | spec-guide |
| 数据模型契约 | 机器可校验（SQL DDL 逻辑子集，sqlglot 深校） | 跨边界数据模型（ER/持久化结构） | spec-guide |
| 完整 spec | 系统级主口径、骨架与术语的唯一锚点 | 整体架构骨架、复杂主口径 | spec-guide |
| 流程图 | 流程逻辑可视化、可评审 | 业务流程对齐 | mermaid-business-flowchart |

## 第三步：路由

- **spec 系**（ADR / 契约文档 / 完整 spec）→ spec-guide 场景 A；既有 spec 的审查与更新分别走其场景 B / C。
- **原型路径**：加载 prototype-standard skill 产出可运行原型，原型即验收物，验收通过即收口，不产出文档形式 spec。原型生命周期刻意压薄：创建 = 普通实现工作，收口 = 验收，退役 = 回写后删除。验收中拍板的决策若涉及契约、边界或状态所有权，必须回写 spec（spec-guide 场景 C）；原型被重写或废弃前回写必须完成。
- **流程图** → mermaid-business-flowchart。
- **落地设计文档形态**（可逆决策但用户明确要求先出设计文档）：产出 `docs/<域>/<主题>-design.md`，设计先行、实现后置；不归 spec 系、不归原型路径。状态机、强制推进点、收口与回写规则见 `references/design-doc.md`；字段与枚举见 spec-guide `references/frontmatter.md` 第四节，`design_lint.py` 强制校验。
- **产物登记**：流程图与原型是无 frontmatter 产物，创建时登记进 `docs/design-registry.yaml`（格式见 spec-guide `references/frontmatter.md` 第五节，`design_lint.py` 执法）；新仓库无登记表时，按 spec-guide 的治理脚手架初始化（`init_design_governance.py`）。

路由结论向用户声明：可逆性判定 + 选定载体 + 理由。载体选择是设计取舍，用户确认后进入对应工作流。

## UI/交互类需求的交付顺序

默认四段式：设计文档（design-doc 形态，含已拍板前提表）→ 零构建交互原型 → 用户评审（单独一轮明确「通过」）→ 才动产品代码。**评审通过前不碰实现**；用户明确要求跳过文档或原型（如「直接改」）时按用户指示；用户明确免审（如「不要让我审核方案」「决策已清晰，直接开干」）时，方向拍板即视为进入实现授权：不再抛待评审决策点与评审请求，设计细节按文档已写倾向落定，评审材料（原型）无人消费时可一并省去。

- 原型交付附「怎么打开」（预览命令 / URL）与「请你重点看哪几处」；评审通过当轮推进设计文档状态与原型登记（written-back），不等提醒。该交付附则对一切渲染视觉产物通用（含验收时效与宿主差异提示），通用形态见 visual-handoff skill。
- 「对现有设计做优化 / 修改」类任务（评审反馈转述）同样按此顺序。
- 半透明叠层文字对比度核验见 prototype-standard skill 的 `references/contrast-stack.md`；底线类决策以脚本数字为依据，不用估计值。

## 边界（Do NOT）

- 不在本 skill 内编写 spec 正文，不定义 spec 的质量判据（归 spec-guide）。
- 不给原型的创建/更新另设流程（原型生命周期压薄是主动设计，不是遗漏）。
- 不做设计层产物的审查：单份走 spec-guide 场景 B，多份对照走 design-review。
- 不重复判断用户已明确指定的载体。
- 需求本身模糊（要什么都没收敛，不只是载体未定）时，先走需求澄清再回本 skill。澄清按能力引用（通用层与客户端分层见 AGENTS.md）：当前环境有澄清类 skill 或可委派的澄清子代理时用之（当前环境：`subagent` / `subagent_fork`；降级：主 agent 内联）；都没有时主 agent 内联执行最小澄清：问清真实目标、目标用户、验收判据、不做清单四件事。形式仲裁：默认 skill 内联澄清（轻、保留主线程上下文）；澄清需要先读大量仓库材料才能问对问题时，委派澄清子代理（隔离探索上下文）。

## 与相关 skill 的衔接

- **spec-guide**：spec 系载体的生命周期工作流；本 skill 只做上游路由，可逆性与载体结论以本 skill 为准。
- **design-review**：多份设计层产物之间的对照审查；本 skill 管新建入口，它管已有产物体检。
- **prototype-standard**：原型路径的工程标准与文件 Schema。
- **mermaid-business-flowchart**：流程图载体的专门工作流。
- **需求澄清（能力引用）**：需求模糊时的上游；形式与降级见「边界」末条。
