# 交付前门禁（delivery-check）

完成开发、修复、重构或 review 后、宣告交付前，逐项确认。每项只给判据与出口；领域规则归对应 skill。

1. **主链走通**：主链/主流程从入口到结果完整可用，问题层级已裁定清楚。
2. **无第二套**：复用了既有主抽象，没有新增第二套入口、契约、状态、术语或流程；被替代的旧说法没有保留。判定细则见 implementation-discipline。
3. **继承面与残留已核验**：本轮触发继承面时（行为/默认值/命名/契约/降级路径/入口/数据形状/外部假设变化），方案中的失效表示清单已逐项处置（`edit`/`delete`/`regen`/`verify`/`delegate`/`na`），`done` 有证据、`delegate` 有 owner、`na` 有探针结果；未触发时说明判据。清单只活在对话，不落盘。同时确认没有留下与用户目标相背的临时脚本、调试产物、废弃草稿；发现非本轮残留时转 sweep skill 执行清理（由用户显式调用）。本 skill 只确认，不执行删除。判据与记录格式见 stale-representation skill。
4. **测试保护当前需求**：本轮行为有测试保护，且测试不是固化的旧行为。测试取舍见 implementation-discipline；失败根因定性见 problem-triage。
5. **设计同步有证据，用户验收有边界**：两条线分别判定，互不替代。
   - **5.1 内部一致性证据**：列出本轮涉及的设计层产物（`<路径> §<节> → edit/delete/verify → done/未核`），与继承面清单同构；`done` 有探针结果，语义项核不了标「未核」并写明跟进 owner，禁止用「本次未涉及」代替判据。相关 spec 已在场景 C 内更新；可逆行为已通过原型验收；评审/实现带来的状态变化已写进产物 frontmatter `status`，不止停留在对话里。字段与状态机见 spec-guide。
   - **5.2 行为验收单**：用产品语言给出「这次能看见什么变化 / 怎么走到 / 预期看到什么 / 这次没动什么」，控制在 5 步以内；用户实际操作确认，或明确免验。agent 不得代宣告用户验收，未确认只能写「待确认」。判据与边界见下文「行为验收」。
6. **阻塞已说明**：如仍有阻塞，已说明阻塞原因、影响范围、当前临时状态、继续条件和未拍板问题。
7. **机制已运转**：本轮交付物含"机制"（校验脚本、门禁、CI 步骤、ignore 规则、索引/map 登记、配置项）时，交付物不是文件本身，而是运转中的机制。逐项确认：(a) 已接入执行链——被 pipeline / 构建 / 入口实际引用，而非只在文档里被要求执行；(b) 已演示一次真实生效——如守卫对违规样本确实报错、ignore 规则与已追踪文件的交集为空；(c) 无悬空引用——声明的 schema / 路径 / 入口实际存在。理由：只落文件、未验证运转的机制是装饰品，还会制造"已治理"的假象，比没有机制更难被发现。
8. **design gate 通过**：本轮新建或改动的设计层产物（spec / ADR / 契约文档 / 落地设计文档 / 登记表条目）已跑 `python3 "$HOME/.agents/skills/spec-guide/scripts/design_lint.py"` 且阻断级为零；提示级命中已显式裁定（修正或声明豁免）。本轮未触碰设计层产物时本项自动通过。
9. **界面文案已过用户视角审查**：本轮改动触及用户可见文案（页面标题、说明段落、空态、错误/成功提示、按钮、占位符、提示气泡、aria-label）时，按 ui-copy-check 的标准过一遍；改动面较大或涉及整页/整流程时，另起一个独立上下文做对抗性复审（优先委派子代理；无子代理能力时，主 agent 只拿标准与改动后的文件复核一遍，不参考改写理由）。判据与改写规则见 ui-copy-check。
10. **门禁结论晚于最后一次编辑**：宣告交付前若又做过任何编辑（含收尾清理、小重构、rebase、依赖或产物重建），此前的门禁/测试结论已过期——必须在**最终代码状态**下重跑交付门禁与入口验证命令到真实变绿，才能宣告交付。「归因证明代码没错」（如全量非增量编译通过、判定为假红）不等于放行：放行的对象是用户要跑的入口命令本身。理由：曾有一次最后一轮清理编辑后未重跑门禁即交付，用户跑入口命令时被同一个报错挡在外面一整轮。
11. **视觉产物已交接人工验收**：本轮交付或确认过带画面的产物时，按 visual-handoff skill 交接：渲染检查已跑并留证；预检结论按「疑似 + 可能漏检」标注、未升格；已附打开方式、重点看哪几处（≤5）与未验项，并明确请求验收。用户明确免审时记免审；用户确认后本轮若再编辑，该次验收作废须重新提交。本轮未触碰视觉产物时本项自动通过。

## 行为验收

- **谁验收什么**：用户只验收他可感知的功能行为；内部文档、注释、契约是否已同步归 5.1，不进验收单——用户无法通过使用产品判断它，列给他只会制造「已处理」的假象。
- **验收单四要素**：本次可见变化、到达路径（打开哪里、点什么，或执行什么命令）、每步预期、本次没动什么（防止把无关变化当成本次结果）。
- **用户可见的腐坏进验收单**：帮助文案、空态、错误提示、按钮用语等旧说法属于可感知范围，写进「本次可见变化」一并确认；内部设计文档的漂移不写。
- **与视觉验收的边界**：功能行为归本项；版式、观感、审美归 visual-handoff（第 11 条）。同一操作可合并成一次确认，但结论分别标注，不得互相顶替。
- **时效**：用户确认后本轮若再编辑，该次确认作废，须重新提交；与第 11 条同构。

## 延期条件

只有存在真实阻塞时才延期：需要用户拍板设计/架构/契约取舍，缺少外部环境、账号、数据或不可替代依赖，当前改动范围超出授权，一次性推进会破坏可验证主链，或必须先完成更上层设计定稿。
