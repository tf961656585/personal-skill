# Spec ↔ 测试双向一致性检查

本文件是 SKILL.md「实现完成后回验 → 一致性校验」的展开，配合 `scripts/trace_acceptance.py` 使用。脚本做机器可校验的追溯，本文件规定追溯的格式约定、漂移分类与人工裁定流程。

适用范围：**spec-anchored** 与 **spec-as-source** 层级（见 `persistence-models.md`）。spec-first 不强制。

## 一、为什么需要双向追溯

SKILL.md 原本的回验是纯人工判读——"实现是否与 spec 一致"靠人读一遍判断。这有两个失败模式：

- **spec 有验收项，但没有测试覆盖它**：验收项成了空话，无人发现。
- **测试存在，但和 spec 对不上**：测试在测 spec 没写的东西（spec 漂移），或 spec 改了测试没跟上（测试漂移）。

双向追溯用机器发现这两类漂移：spec 的每个验收项都能找到对应测试，每个 `@spec` 标注的测试都能在 spec 中找到验收项。

## 二、验收项格式约定（spec 侧）

spec 中每个可测试的行为点必须用标准格式标记，供脚本扫描。两种格式二选一，混用允许但同一 spec 内建议统一。

### 格式 A：Given/When/Then（场景式）

```markdown
#### 验收：PAY-001 创建订单成功

- Given 用户已登录且购物车非空
- When 用户提交订单且库存充足
- Then 生成订单记录，返回订单 ID，扣减库存
```

ID 规则：`<域缩写>-<序号>`，如 `PAY-001`、`AUTH-002`。ID 在 spec 内唯一，是追溯主键。

### 格式 B：EARS（需求式）

```markdown
#### 验收：AUTH-001

WHEN 用户提交错误密码连续 5 次，系统 SHALL 锁定该账号 30 分钟。
```

EARS 五模式：
- 事件型 `WHEN <事件>, 系统 SHALL <动作>`
- 状态型 `WHILE <状态>, 系统 SHALL <动作>`
- 异常型 `IF <异常>, THEN 系统 SHALL <动作>`
- 可选型 `WHERE <能力>, 系统 SHALL <动作>`
- 普适型 `系统 SHALL <动作>`

### 扫描规则（脚本侧）

`trace_acceptance.py` 识别以下模式为验收项：
- 四级标题 `#### 验收：<ID>` —— ID 为标题中的标识符。
- 行内 EARS 关键字 `WHEN/WHILE/IF/WHERE` + `SHALL`，且附近有 `验收：<ID>` 标记。

无 ID 的验收项会被脚本报告为"未编号验收项"（提示级，不阻断）。

### 编号稳定性：禁止复用旧号承载新语义

验收项 ID 是跨 spec 与测试的稳定主键，一旦分配就与**那一条行为描述**绑定。改 spec 时按三种情形区分：

- **行为描述变更**（口径修订、范围扩缩、措辞重写）→ 沿用原 ID。这是验收项的正常演进，测试标注无需改动。
- **删除后由另一含义的新项顶替** → 新项分配**未占用**的号，不得沿用被删项的号。
- **新增验收项** → 取该 spec 编号序列中下一个未占用的号，保持连续。不要为"预留"或"避让"而跳号——中间的空洞会让后续读者误以为那些号曾存在过又被误删。

这条纪律的必要性来自脚本的检测盲区：`trace_acceptance.py` 按 ID 字符串做双向追溯。若把旧 ID 换上新描述，测试侧 `@spec: <旧ID>` 的标注依然"对得上"——ID 存在、有测试覆盖，追溯全绿，但那个测试断言的可能完全不是新描述的行为。换言之，**编号复用会让追溯信号失真而不自知**：orphan/missing 两类阻断级漂移一个都不报，语义却已经漂移。因此人工判读时，把"这个 ID 的语义是否在本轮被换过"列为固定检查项（与 §七 已声明的"脚本做不了语义校验"是同一条边界）。

改号后必须 grep 全仓库确认无残留引用——其他 spec 的交叉引用、原型导航注释、`memory/` 里引用的 ID 都会指向不存在或已无关联的验收项。

## 三、测试标注约定（测试侧）

测试用例用 `@spec: <验收项ID>` 标注其覆盖的 spec 验收项。标注写在测试名注释、文档字符串或紧邻的注释中。

各语言示例：

```python
# Python (pytest)
def test_create_order_success():
    """@spec: PAY-001"""
    ...
```

```typescript
// TypeScript (jest/vitest)
test('create order success', () => {
  // @spec: PAY-001
  ...
})
```

```javascript
// JavaScript 注释行也识别
// @spec: PAY-001
```

### 标注规则

- 一个测试可标注多个 `@spec:`（覆盖多个验收项）：`@spec: PAY-001, PAY-002`。
- 一个验收项可被多个测试覆盖（正常路径 + 边界 + 异常各一个测试）。
- 标注格式固定为 `@spec: <ID>`，冒号后空格可选，ID 不带引号。

### 标注书写陷阱（解析器实测）

- 标注必须**独占一行注释**，内容只写 ID 列表（`// @spec: PAY-001, PAY-002`）。写在测试标题字符串里时整行都会被抓取；标注行夹带英文散文词（如 Esc、Escape 等任何 ASCII 词）会被 ID token 校验误解析成多余 ID，报「孤儿测试」阻断级。中文散文安全（不匹配 ID token），英文不安全。
- 编号写在 `describe()`/`it()` 标题字符串里**不构成标注**（脚本只认 `@spec:` 注释行）——标题里带 ID 只是给人看的，测试侧仍须有独立 `// @spec: <ID>` 注释行。
- 多个 ID 分隔只用**逗号**（顿号不解析）。扫描白名单 `TEST_FILE_SUFFIXES` 已含 `.mts`/`.cts`（2026-10-07 补：desktop-shell 全部测试是 `.test.mts`，白名单缺失时该目录标注整体不可见、覆盖率假低）——修改脚本时勿移除。
- `trace_acceptance.py --tests` 可重复传参扫描多个目录（spec 的测试分散在 app 测试、共享包测试、守卫夹具等多处时一次跑全，并集判读覆盖率）。

### 扫描规则（脚本侧）

`trace_acceptance.py` 在测试目录扫描所有文件，提取 `@spec: <ID>` 标注。识别 ID 列表（支持逗号分隔多个）。

## 四、三类漂移

脚本输出以下分类报告：

### 1. 缺失测试（Missing Test）— 阻断级

spec 有验收项 `<ID>`，但测试目录中无任何 `@spec: <ID>` 标注。

含义：spec 声明了行为，但没有测试验证它。可能是：
- 验收项漏实现/漏测 → 补测试。
- 验收项过时 → 走场景 C 删除或修订验收项。

裁定：必须二选一，不允许"spec 说了但没测"长期存在。

### 2. 孤儿测试（Orphan Test）— 阻断级

测试标注了 `@spec: <ID>`，但 spec 中找不到验收项 `<ID>`。

含义：测试在测 spec 没声明的东西。可能是：
- spec 删了验收项但测试没删 → 删测试或恢复 spec 验收项。
- ID 写错 → 修正标注。
- spec 漏写 → 补 spec 验收项（走场景 C）。

裁定：必须查清来源，不允许"测了但 spec 没说"长期存在。

### 3. 未标注测试（Unannotated Test）— 提示级

测试文件中没有任何 `@spec:` 标注。

含义：可能覆盖了 spec 验收项但没建追溯，也可能是纯实现细节测试。脚本不阻断，仅提示数量。

处理建议：鼓励为行为级测试补标注；纯实现细节测试（如测某私有函数）可不标注。

## 五、漂移裁定流程

脚本发现漂移后，按以下流程裁定（对接 spec-guide 场景 C）：

```
脚本报告漂移
  ├─ 缺失测试（spec 有、测试无）
  │    ├─ 该验收项仍有效 → 补测试（实现侧动作）
  │    └─ 该验收项过时   → 场景 C：删除/修订验收项（spec 侧动作）
  │
  ├─ 孤儿测试（测试有、spec 无）
  │    ├─ ID 写错        → 修正标注（实现侧动作）
  │    ├─ spec 漏写      → 场景 C：补验收项（spec 侧动作）
  │    └─ spec 删过      → 删测试或恢复（双方裁定）
  │
  └─ 未标注测试（提示）
       └─ 行为级测试鼓励补标注；实现细节测试可不标注
```

脚本无报告时的补充判读（机器看不见的漂移，见 §二「编号稳定性」与 §七）：

- **验收项语义被换过**：本轮若重定义或顶替过某个 ID，脚本不会报任何漂移，须人工核对测试断言是否仍匹配新描述；换号的情形还要 grep 残留引用。

**关键纪律**：漂移裁定结果若是 spec 侧变更（补/删/改验收项），必须走场景 C 完整流程（含变更记录），不能直接改 spec。脚本只发现漂移，不直接改 spec 或测试。

## 六、何时运行

- **spec-anchored / spec-as-source 层级，实现完成后回验**：必跑（见 SKILL.md 回验章节）。
- **场景 C 变更 spec 验收项后**：必跑，确认测试覆盖同步。
- **定期/CI**：建议接入 CI，spec 验收项变更时自动触发。

## 七、脚本的边界

`trace_acceptance.py` 只做**追溯关系**校验（ID 是否对得上），不做：
- 语义校验（测试是否真的测了验收项描述的行为）——这需要人工判读。
- 测试通过率校验——这是测试运行器的事。
- 验收项质量校验——这是场景 A3 自检的事。

脚本覆盖不到的语义层，由人工判读补充：回验时除了跑脚本，还要人工抽查"标注对上的测试，其断言是否真的验证了验收项描述的行为"。

### 覆盖率是代理读数，不是状态机

脚本输出的"覆盖率（`已覆盖/总数`）"回答的是"验收项有多少已被测试标注触达"，**不是**实现完成度。刻意的口径：

- **未覆盖 ≠ 未实现**：spec 是应然，验收项是目标行为；没有测试只说明"该目标行为没有可执行的对错标准"，不说明代码没做。
- **有测试 ≈ 已实现**：测试存在是实现状态的**代理信号**，但权威口径永远以代码为准——测试可能断言的是旧行为（见 implementation-discipline「测试保护当前需求」）。
- 因此覆盖率**不设阈值、不进入任何状态机**。它的用途是给 agent 消费 spec 时一个低成本的"哪些验收项值得先去代码里核实"的优先级提示，把"每次都要全量核实"的成本降下来。要确认某验收项的真实实现状态，仍须按 project-entry 的发现链回到代码核实。
