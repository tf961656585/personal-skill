# Spec 编写、审查与维护工作流

本 skill 是处理 spec 的唯一工作流。所有涉及 spec 编写、审查、更新、维护的场景，都必须走本工作流。

## 适用范围

- **适用**：编写新 spec、审查已有 spec、更新/维护 spec、讨论 spec 质量、实现完成后回验 spec、编写 ADR 式决策记录。
- **不适用**：纯代码实现讨论（无 spec 变更）、阶段计划编写、排查过程记录。

## 前置分流与产物类型

载体的可逆性判定与选择由 design-guide 唯一负责：被 design-guide 路由进入本工作流时，以其结论为准；用户直接指定 spec 系载体时直接进入场景判断；若发现载体未定，退回 design-guide。

- 落地设计文档（design-doc）不属本工作流；其中评审拍板的契约/边界/状态所有权决策按场景 C 回写 spec/ADR，纯交互细节不回写。
- 原型验收中拍板的契约/边界/状态所有权决策同样回写 spec/ADR（场景 C）。
- 行为级测试是验收的可执行形式（Specification by Example）：spec/ADR 是人读的裁决记录，测试是机器执行的对错标准；验收标准是测试的子集，显式标注"完成"判据。
- 执行计划 / task 是易变 delta，用完可丢弃，不长期维护，不反向覆盖 spec。

## 持久化层级与变更模型

进入本工作流并选定载体后，先定生命周期层级（spec-first / spec-anchored / spec-as-source）与变更模型（Flow-Back / Flow-Forward / Living Spec），结果写进 frontmatter。选择器、各层保鲜纪律与常见误用见 `references/persistence-models.md`；字段与取值见 `references/frontmatter.md`。

默认是 spec-anchored + Living Spec：与代码同步演进、实现完成后回验、走完整场景 C。spec-first 用完即弃，不进入状态机；spec-as-source 要求代码由 spec 派生，改代码前先改 spec。

⚠️ 若实现过程中发现 spec-first 的决策实际不可逆（架构骨架、核心契约），立即升级为 spec-anchored 并补走场景 A 收口，禁止"用完即弃"丢弃不可逆决策。

## Spec 生命周期管理

spec-anchored / spec-as-source 层级的 spec 必须纳入生命周期状态机。完整状态机、定稿历史化流程、退役归档、复审触发见 `references/lifecycle.md`；字段与取值见 `references/frontmatter.md`。

三条常用判定保留在此：
- **定稿历史化**：同一节 3 次以上补丁式修订，或修订触及核心契约/状态所有权，判定为大改——新开 spec 取代旧 spec，不无限改写活文档；小改走场景 C 变更记录。
- **退役**：不再用时标 `Deprecated` → 引用清理完成 → `Archived`；不复活旧文档，需恢复口径则新开 spec。
- **大改破锚**：判定为大改时，先委派破锚解构子代理产出四分类报告（真约束/锚/待改写/待删除），再以报告为基础走场景 A；机理与编排见 `references/spec-refactoring-anti-anchoring.md`。

## spec 的身份与纪律

* spec 指不在代码运行时直接发挥功能、但作为开发参照物的稳定文档集合，只承载不可逆决策：架构骨架、契约语义、状态所有权、边界、职责、术语与主口径。文档是否属于 spec 不取决于目录或文件名，而取决于它是否定义长期稳定的目标、边界、契约、术语或主口径。
* spec 是目标状态（应然），代码与原型是现状（实然）；证据等级与断言纪律见 AGENTS.md「应然与实然」，不在此重复。
* 涉及业务闭环、业务规则、职责边界、协作关系、契约语义、术语定义、角色权限、治理规则或关键约束变化时，属于 spec 变更。spec 变更必须先完成口径收口再进入实现，禁止并行漂移；实现中发现任务实际触发 spec、契约或主抽象变更时，立即停止局部实现，先上浮裁定。
* 若实现与已收口 spec 不一致，必须判断是 spec 需要变更还是实现偏离 spec，并收口为单一口径。非 spec 材料不得反向覆盖 spec；过程材料发现 spec 有误时，先上浮裁定再更新 spec。
* 原型存续期间是可逆行为的事实源；原型被重写或废弃前，其中涉及不可逆决策的部分必须已回写 spec，不允许决策只活在旧原型里。
* spec 是迭代的，不是一次性文档。实现与原型验收中产生的架构决策、契约变更、边界裁定，必须回写 spec/ADR，保持 spec-anchored（spec 作为长期锚点与代码同步演进）。禁止实现跑在 spec 前面、事后不回写，导致 spec 腐化为死文档。
* spec 的详略由风险与关键性驱动：低关键性场景可简单记录快迭代；高关键性场景（涉及资金、用户数据、跨进程契约等）必须详尽严控。
* spec 沟通使用自然语言，不掺杂代码引用；进入代码开发层沟通后，才使用技术风格和代码引用。

## 文档格式与风格

* 人类阅读优先时使用 Mermaid，表达简洁干练，可中英文双语；agent/机器阅读优先时使用 YAML；人类和机器都需要良好可读性时使用 Markdown。
* 面向人类架构师/开发者的 spec 文档应可读性高、精简干练、高内聚，服务业务设计和架构设计。
* 面向 agent 的入口文档（项目根 `AGENTS.md`）保持轻量，只声明稳定规则与跳转入口；目录结构承担第一层导航，只有目录结构无法稳定表达的任务路由、主口径优先级、废弃关系、阅读顺序与例外规则，才进入专用 map 文件。
* 详细阅读地图、任务路由、文档分发关系、当前主口径与废弃关系，放入 `docs/agent-map.yaml` 或其指向的拆分文件，按需加载，不要求默认通读；它必须服务于收口后的主 spec 口径，不能形成第二套 spec 口径。

## 工作流总览

本工作流覆盖三种场景，每种场景有独立的阶段流程：

| 场景 | 触发条件 | 阶段 |
|------|----------|------|
| A. 编写新 Spec | 从零创建 spec，或将散乱信息整理为正式 spec | A1→A2→A3→A4 |
| B. 审查已有 Spec | 对**单份 spec** 做内部质量审计（完整性 / 可验证性 / 时态 / 内部单一真实性） | B1→B2→B3→B4 |
| C. 更新/维护 Spec | 需求变更、实现发现、review 意见等触发的 spec 修改 | C1→C2→C3→C4 |

跨产物对照（多份文档对不对得上）不归场景 B，走 design-review。

## 场景判断

进入工作流时，首先判断当前属于哪种场景：

1. **不存在相关 spec** → 场景 A（编写新 Spec）
2. **已有 spec，用户要求审查或检查质量** → 场景 B（审查已有 Spec）
3. **已有 spec，需要因变更而修改** → 场景 C（更新/维护 Spec）

如果不确定，向用户确认。

## 场景 A：编写新 Spec

### 阶段 A1：准备

**目标**：建立上下文，明确边界。

1. 读取相关既有 spec（架构概览、术语表、关联系统 spec），理解当前 spec 生态。
2. 明确本 spec 覆盖的系统/模块边界：
   - 本 spec 管什么（目标）
   - 本 spec 不管什么（非目标）
   - 与其他 spec 的职责分界线
3. 确认术语归属：哪些术语已在术语表中定义，哪些需要在本 spec 中新增定义。

**产出**：spec 边界与上下文摘要（内含即可，不必单独输出）。

### 阶段 A2：编写

**目标**：按结构模板产出 spec 初稿。

推荐结构（按需裁剪，不是所有节都必须）：

1. **背景与目标**：为什么需要这个系统/模块，解决什么问题。
2. **非目标**：明确声明本次不覆盖的事项。
3. **术语定义**：本 spec 新增或特别约定的术语。已在术语表中的术语引用即可。
4. **核心概念与关系**：主实体、主链路、实体间关系（包含、依赖、互斥、组合）。
5. **接口/契约定义**：输入、输出、前置条件、后置条件、错误码。
6. **数据模型**：核心字段、类型、约束。跨边界数据模型必须落 SQL DDL 契约文件（形态 C，骨架见 `references/templates.md`），spec 内引用该文件，不用散文或表格双写。
7. **状态转换**：完整状态集、合法转换、非法转换的处理。
8. **边界条件与异常处理**：并发、超时、空数据、降级等极端场景。
9. **可观测性要求**：需要记录的事件、关键指标、诊断路径。

**编写纪律**：

- **时态卫生**：spec 是应然文档，只描述目标终态，不描述现状。禁止在 spec 中混入当前代码现状、实现进度（已落地/未落地标记）、阶段计划、迁移流水、排查过程、临时 TODO 或证据记录。spec 只对"最终应该是什么样"负责，不对"现在做到哪一步"负责。
  - **阶段词禁令**：spec 中禁用"首批/批次/首期/阶段 N/暂不启用/先…后…"等阶段词——机制要么定义要么不定义，"框架已定义但暂不启用"是计划不是设计。落地批次、收口顺序、优先级建议属计划层，只在对话中对齐，不写入 spec 任何章节（含待决策项的措辞）。
  - **时态自检口诀**：拿不准某句话是否属于现状污染时，问"这句话拿掉后，spec 描述的目标状态变不变"。不变 → 是现状/进度描述，删；变 → 是目标定义，留。
- spec 禁止写成代码实现指南。定义接口、行为和数据结构，不教怎么写 if-else 或给出具体伪代码。
- 严禁模糊、主观词汇（"尽量"、"可能"、"大概"、"最好"、"看情况"）。只使用确定性语言：必须（Must/Shall）、应当（Should）、不得（Must Not）。
- 首次出现的术语必须有定义。禁止堆砌没有上下文的技术名词。
- 能用图表（时序图、状态机图、表格）表达的，不用纯文字。能用表格表达的映射关系，不用列表罗列。
- **验收项创建即配 `@spec:` ID**：spec-anchored / spec-as-source 层级的验收项，创建时就用标准格式编号（见 `references/consistency-checks.md` 第二节），不要等补测试时才回填。理由：测试覆盖是实现状态的唯一代理信号——`trace_acceptance.py` 的覆盖率读数（已覆盖/总数）是 agent 消费 spec 时"哪些验收项该先去代码里核实"的优先级提示；验收项无编号，这个代理读数就无从产生。覆盖率是代理读数不是状态机（口径见 consistency-checks.md 第七节）。

### 阶段 A3：质量自检

**目标**：用检查清单逐项验证 spec 质量。发现问题回到 A2 修正，直到全部通过。

#### 背景与目标
- [ ] 是否明确解释了为什么要做这件事（商业价值/用户痛点）
- [ ] 是否明确定义了非目标
- [ ] 是否说明了与现有系统的关系和影响范围

#### 术语与概念
- [ ] 是否定义了所有关键术语，且定义唯一、无歧义
- [ ] 术语在全文中的使用是否一致，有无同名异义或异名同义
- [ ] 核心概念之间的关系是否清晰（包含、依赖、互斥、组合）

#### 技术与数据
- [ ] 数据模型或核心字段定义是否完整、类型是否明确
- [ ] 接口的输入、输出、状态码及错误码是否定义清晰
- [ ] 状态转换是否完整（所有状态、所有合法转换、所有非法转换的处理）

#### 边界与异常
- [ ] 并发、幂等性、大流量、超时等极端情况是否有处理方案
- [ ] 权限控制是否考虑周全
- [ ] 数据一致性保障是否定义

#### 时态纯净度
- [ ] spec 是否只描述目标终态，有无混入当前代码现状（"现在是这样""目前用 X 实现"）
- [ ] 有无实现进度标记（"已实现""待开发""Phase 1/2""TODO 后续补"）
- [ ] 有无阶段计划、迁移流水、排查过程、证据记录等非 spec 内容混入

#### 可验证性
- [ ] 每个功能点是否能直接转化为测试用例
- [ ] 验收标准是否明确、可量化
- [ ] 是否有模糊不清的断言需要澄清

#### 单一真实性
- [ ] 对同一概念是否只有一个口径，无多线定义或口径漂移

### 阶段 A4：集成检查

**目标**：确保新 spec 与既有 spec 生态一致。

1. **冲突检测**：新 spec 的术语、契约、边界是否与既有 spec 冲突。如有冲突，裁定为单一口径。
2. **术语同步**：新 spec 新增的术语是否需要同步到术语表。
3. **影响面**：新 spec 是否影响其他 spec 的内容。如有，必须同步更新受影响 spec。
4. **单一口径**：确认没有制造第二套入口、契约、状态、术语或流程。对同一对象、模块或系统，只能存在一条主 spec 口径。

**产出**：完整的 spec 文档 + 相关 spec 的同步更新。

## 场景 B：审查已有 Spec

### 阶段 B1：通读理解

1. 读取目标 spec 全文。
2. 读取关联 spec（架构概览、术语表、上下游系统 spec）建立上下文。

### 阶段 B2：质量审计

用 A3 的质量检查清单逐项审计，标注每项的通过/不通过状态和具体问题。

### 阶段 B3：内部一致性与线索收集

1. 检查目标 spec 是否存在多线定义（同一概念有多个定义）。
2. 检查目标 spec 是否包含阶段计划、排查过程等不属于 spec 的内容。
3. **跨产物矛盾只收线索不做权威对照**：审计中发现目标 spec 与其他 spec 可能术语不一致、口径冲突、职责重叠的线索时，不在本场景展开、不写入 B 报告结论——记录为"另起 design-review 任务"的线索一句话带过。跨产物对照的权威审查归 design-review（见 description 的"不适用"）。

### 阶段 B4：审查报告

产出结构化审查报告：

```markdown
## Spec 审查报告：[spec 名称]

### 总体评价
[通过 / 有条件通过 / 不通过]

### 严重问题（阻断级）
1. [问题描述 + 修改建议]

### 一般问题
1. [问题描述 + 修改建议]

### 改进建议
1. [建议内容]

### 通过项
[列出通过的关键检查项]
```

## 场景 C：更新/维护 Spec

### 阶段 C1：变更评估

1. **变更来源**：确定触发变更的原因。常见来源：
   - 需求变更、实现发现、review 意见、bug 修复
   - 原型验收中拍板的契约/边界/状态所有权决策回写
   - **reflect 提案**——reflect 在 `memory/proposals/` 发现 spec 矛盾或双线实现时，提案转本场景收口（衔接 reflect Step 4）
   - **测试变更**——测试用例增删改触发对关联 spec 验收项的检查（衔接 `scripts/trace_acceptance.py` 的反向追溯，孤儿测试即典型信号）
   - **sweep 清理发现**——sweep 扫到"与本轮结论矛盾的旧口径"且对象是 spec 时，转本场景收口（衔接 sweep 执行流程）
2. **变更范围**：哪些 spec 节受影响。
3. **影响面**：变更是否波及其他 spec。
4. **变更性质**：是 spec 需要变更，还是实现偏离了 spec。如果不确定，先上浮裁定。

### 阶段 C2：执行变更

1. 更新受影响的 spec 节。
2. **变更即清理**：不仅补写新口径，还必须删除、改写或降级旧口径。禁止只加不删。删旧口径、清理交叉引用、同步 `agent-map.yaml` 导航等 spec 文本清理在本场景内完成；任务收尾的工作区残留（临时文件、日志、调试产物）转 sweep，不在本场景处理。
3. 更新受影响的术语定义（本 spec 内或术语表中）。
4. 同步更新受波及的其他 spec。

### 阶段 C3：一致性检查

1. 变更后的 spec 是否与整体 spec 生态一致。
2. 是否引入了新的口径冲突或术语漂移。
3. 对同一概念是否仍然只有一条主口径。
4. 变更后的 spec 是否仍然不包含阶段计划、排查过程等非 spec 内容。
5. **别处对 § 编号的引用是否仍然成立**：删节、重编号或重写章节后，其他 spec 与代码注释里的 `§X.Y` 会静默指向错误内容——`design_lint.py` 只保证被引文件存在，不保证被引章节存在。跑 `python3 "$HOME/.agents/skills/spec-guide/scripts/check-section-refs.py" <仓库根>` 扫一遍。它只校验写全文档路径的引用（零噪声），同文档裸 `§1.2` 因归属无法机械判定不在覆盖内。历史注记里叙述旧编号是合法的，所以逐条判、不阻断。

### 阶段 C4：变更记录

在 spec 中追加变更记录：

```markdown
## 变更记录

| 日期 | 变更内容 | 变更原因 | 影响范围 |
|------|----------|----------|----------|
| YYYY-MM-DD | [具体变更] | [触发原因] | [受影响的 spec 节/文件] |
```

## 实现完成后回验

实现完成后，agent 必须主动回验：

1. 实现是否与 spec 一致。
2. 实现是否引入了 spec 未覆盖的新规则、新契约、新状态流或新职责边界。
3. 如有偏差，判断是 spec 需要更新还是实现需要修正，裁定后执行场景 C。

### 一致性校验（spec-anchored / spec-as-source 必跑）

spec-anchored 与 spec-as-source 层级的 spec，回验时必须运行校验脚本，不能只靠人工判读。两台校验器分工：

**① frontmatter 与断链校验（全部设计层产物通用）**：

```bash
python3 "$HOME/.agents/skills/spec-guide/scripts/design_lint.py" docs --root .
```

校验机器可读头部（必填字段、枚举、条件字段配套）、断链（frontmatter 路径字段与 Markdown 相对链接）、变更记录节存在性、产物登记表双向一致性（流程图/原型的生命周期执法，含原型"回写→退役删除"的有尾检查）、agent-map 与 frontmatter 的状态一致性（存在即校验）、时态纯净度（提示级）；OpenAPI 契约在 `openapi_spec_validator` 可用时自动接入深度校验，SQL DDL 数据模型契约在 `sqlglot` 可用时自动接入深度校验（语法解析、外键引用完整性、逻辑子集纪律）。阻断级未清零前产物不得视为已收口。字段与登记表规范详见 `references/frontmatter.md`。全量产物清点用 `python3 "$HOME/.agents/skills/spec-guide/scripts/design_lint.py" docs --root . --list-artifacts`（派生索引，不入库）。

**② 验收项↔测试双向追溯校验**：

```bash
python3 "$HOME/.agents/skills/spec-guide/scripts/trace_acceptance.py" --spec <spec 文件> --tests <测试目录>
```

脚本输出三类漂移（格式约定与漂移分类详见 `references/consistency-checks.md`）：
- **缺失测试**（阻断级）：spec 有验收项，测试目录无对应 `@spec:` 标注。
- **孤儿测试**（阻断级）：测试标注了 `@spec: <ID>`，但 spec 中无该验收项。
- **未标注测试**（提示级）：测试文件无任何 `@spec:` 标注。

阻断级漂移必须裁定后进场景 C（补测试 / 改 spec / 修标注三选一）。人工判读仅作脚本覆盖不到的语义层补充——抽查"标注对上的测试，其断言是否真的验证了验收项描述的行为"。spec-first 层级不强制跑脚本②（脚本①对全部 spec 系产物强制）。

## 质量原则

- **写不清通常是没想清**：spec 中反复改同一段、无法简洁概括行为时，停下来重新看设计本身。
- **对不可逆决策慢即是快**：编码前收口契约与主口径；可逆决策的"想清楚"载体是可运行原型，不是文档。修复成本的数量级差异只是经验值，不是承诺。
- **悲观设计**：假设网络会断、服务会降级、用户会乱填、并发会突增；每个"如果……怎么办"都要有回答。
- **沟通即减熵**：两人对同一行为描述不一致，说明该处 spec 缺失、模糊或矛盾。

## 快速参考

核心纪律：
- **单一真实性**：同一概念只能有一条主口径
- **变更即清理**：补写新口径的同时删除旧口径（在场景 C2 内完成）
- **定稿即历史**：大改新开 spec 并链接取代关系，不无限改写活文档
- **spec 身份**：不承载实现细节、阶段计划、排查过程、当前代码现状或临时 TODO
- **实现不反向覆盖 spec**：实现偏离时，先裁定是 spec 需要变更还是实现需要修正
- **双向追溯**：spec-anchored/as-source 层级的验收项必须有对应测试覆盖（`@spec:` 标注）
